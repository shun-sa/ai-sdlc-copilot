# 非機能要件定義書：MiniCommerce

## 0. 文書管理

### 0.1 改訂履歴

| 版数 | 日付 | 改訂内容 | 作成・改訂者 |

## 1. 本書の目的と適用範囲

### 1.1 目的

本書は、株式会社あおば雑貨（以下「当社」）の自社ECサイト MiniCommerce が満たすべき機能以外の品質条件（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、ユーザビリティ・アクセシビリティ、システム環境・技術制約、法令準拠）を、検証可能な目標値・測定条件・検証方法とともに定義する。本書の利用者は、MiniCommerce の設計・開発の担当者、試験（性能テスト・セキュリティテスト・運用テスト）の担当者、受入を判定する当社の EC事業責任者・システム運用担当である。

### 1.2 適用範囲

| 区分 | 内容 |
|---|---|
| 対象システム・範囲 | MiniCommerce の全体。具体的には、来訪者・購入者向けの Web画面（PCブラウザ）と Web API（JSON/REST）、管理者（EC運営担当・出荷担当）向けの Web画面と Web API、運用者（システム運用担当）がサーバー上で実行する初期データ一括投入コマンド、本システム内に実装する決済サービスの模擬機能（模擬決済）を対象とする。 |
| 対象環境 | 本番環境（ENV-02）。本番環境の基盤は未選定のため、本リリースの検証は開発・検証環境（ENV-01）で行い、ENV-01 で測定できない指標は 12.3 の扱いに従う（環境の定義は 12.1）。 |
| 本書で定義しない | 機能ごとの権限の割当（本書のセキュリティはシステム全体の方針・基準の水準で記述する） |
| 本書で定義しない | 非機能要件を実現する具体的な構成・製品設定・パラメータ値（本書は満たすべき条件と目標値までを記述する） |
| 本リリースの対象外 | 次の事項は本リリースで実現しないため、本書の要件の対象としない。実決済サービスとの連携（FR-OUT-01。本リリースは模擬決済で代替）、マスタ保守の画面・API（FR-OUT-02）、メールによる通知（FR-OUT-08）、会員情報の変更・パスワード再設定・退会（FR-OUT-09）、認証失敗時のアカウントロック・ログイン試行回数制限（FR-OUT-11）、未払い注文の自動キャンセル（FR-OUT-12）、商品画像・商品レビュー・お気に入り・おすすめ表示（FR-OUT-13）、スマートフォン専用画面（FR-OUT-14）、帳票（PDF・CSVのファイル出力）（FR-OUT-15）、「特定商取引法に基づく表記」の静的ページ（FR-OUT-16）、多言語・多通貨・海外配送（FR-OUT-06）、保存期間を経過したデータの自動削除機能（削除は運用者が年1回手順に従って実施する）。 |

## 2. 前提となるシステム特性

| 項目 | 内容 |
|---|---|
| システムの概要 | 当社初の自社ECサイトとして、会員向けに WEB受注（商品閲覧→カート→クーポン適用→注文確定→支払→出荷→配達完了）を提供し、在庫と注文の整合、金額計算の自動化、注文状況の可視化を実現する。購入者・管理者向けの Web画面（PCブラウザ）と、同じ業務ルールに従う Web API（JSON/REST）を提供する。稼働開始予定は 2027-04-01。 |
| システムの重要度 | 停止時は、当面併存する通信販売の電話・FAX受注で注文受付を代替できるため、停止による業務影響は限定される。影響を受ける社外の利用者は当社の会員（購入者）と来訪者に限られる。一方、在庫・金額の誤りは二重販売・購入者への誤請求につながるため、データの整合性（在庫数量が0未満にならないこと、金額が規則どおりであること）は停止時間より優先して確保する。 |
| 参照する非機能要求グレードのモデル | 社会的影響が限定されるシステム |
| 利用形態 | 社外公開。来訪者・購入者はインターネット経由で PCブラウザから利用する。管理者（EC運営担当・出荷担当）も PCブラウザから利用する。運用者はサーバーにログインしてコマンドを実行する（Web画面・APIは使わない）。 |
| 利用者区分と利用者数 | 来訪者（ACT-001。未ログインの閲覧者）：不特定／購入者（ACT-002。会員）：稼働時 0人、稼働後1年 3,000人、3年後 10,000人／管理者（ACT-003。EC運営担当3人＋出荷担当4人）：7人／運用者（ACT-005。システム運用担当）：2人 |
| 同時利用者数 | 平常時 30人／ピーク時 150人（購入者＋来訪者の合計。これとは別に管理者が同時最大5人、運用者が同時最大1人） |
| 業務量 | 平常時 100件/日／ピーク時 400件/日（注文件数。12月の繁忙日・クーポン配布初日）。1日の注文の30%が 20:00〜21:00 の1時間に集中するため、ピーク時間帯は 120件/時。1注文あたり平均3明細・平均5点。決済要求は平均 110件/日、ピーク 130件/時（否認後の再支払を含む）。会員登録は平均 9人/日、ピーク 50人/日。 |
| 業務時間帯・繁忙期 | WEB受注：24時間365日（計画停止を除く）。EC運営：平日 9:00〜18:00。出荷：平日 10:00〜17:00（支払済の注文は翌営業日までに出荷登録）。配達完了登録：配送業者の配達完了情報の確認後、翌営業日まで。繁忙期：12月は平常月の2.0倍、7月（夏季セール）は1.5倍。 |
| データ量 | 初期 1,157件／年間増加 486,000〜486,500件（主要データの合計。初期：管理者7件・仕入先20件・商品分類30件・商品300件・在庫単位800件。年間増加：注文 36,500件・注文明細 110,000件・配送先 36,500件・決済記録 40,000件・注文状態履歴 110,000件・会員 3,000〜3,500件・監査ログ 150,000件。3年後：注文 110,000件・注文明細 330,000件・注文状態履歴 330,000件・決済記録 120,000件・会員 10,000件・商品 600件・在庫単位 1,600件・商品分類 45件・仕入先 35件・クーポン 150件） |
| 想定運用期間 | 5年 |
| 外部連携の有無 | 1件。決済サービス（決済要求：注文番号・決済金額・通貨 JPY を送り、承認／否認を受け取る同期連携）。本リリースは本システム内の模擬機能（模擬決済）で実現し、外部ネットワークには接続しない。メール・配送業者・会計システムとの連携はない。 |

## 3. 非機能要件の記述方式

### 3.1 要件表の列定義

| 列名 | 記述内容 | 記入ルール |
|---|---|---|
| ID | 要件の一意識別子 | 本書内で一意のIDを付与する。形式は NFR-AV-xx（可用性）／NFR-PF-xx（性能・拡張性）／NFR-OM-xx（運用・保守性）／NFR-MG-xx（移行性）／NFR-SC-xx（セキュリティ）／NFR-US-xx（ユーザビリティ・アクセシビリティ）／NFR-EN-xx（システム環境・技術制約）／NFR-LG-xx（法令・規約・標準）とする。監視は MON-xx、ログは LOG-xx、脆弱性対策は VUL-xx、環境は ENV-xx、検証データは VDC-xx、差異は DIF-xx、前提条件・制約事項は NCN-xx、未決事項は NOQ-xx とする |
| 区分 | 章内の中分類 | 各章の表に予め記載した区分を用いる。行を追加する場合も同じ粒度の区分とする |
| 要件項目 | 要件の対象を表す名称 | 1行に1項目とし、複数の要件を1行に詰め込まない |
| 要件内容 | 満たすべき状態・条件 | 「〜すること」の形で、対象（機能・データ・利用者・構成要素）を明記して記述する |
| 指標 | 達成度を判定する尺度 | 数値指標（例：応答時間、稼働率、件数）または状態指標（例：有無、方式、準拠レベル）を記述する |
| 目標値（単位付き） | 合格基準となる値・状態 | 数値には単位と判定条件（以内／以上／以下）を付ける。状態指標は第三者が合否を判定できる状態を記述する。空欄不可 |
| 測定条件 | 目標値を測る条件 | 負荷（同時利用者数・リクエスト数）、データ量（件数）、環境（12.1 の環境ID）を記述する |
| 検証方法 | 目標値の達成を確認する手段 | 3.2 の検証方法から選び、確認内容を補足する。空欄不可 |
| 優先度 | 必須／推奨／任意 | 必須＝リリースに不可欠、推奨＝可能な限り実現、任意＝余裕があれば実現 |
| 根拠 | 要件が必要となる理由 | 法令、契約、社内規程、業務上の理由、実績値のいずれかを文章で記述する。本書内の他の要件・表と関連する場合は、本書内の関連する項目のIDを併記する。「該当なし」の行は該当しない理由を記述する |

### 3.2 検証方法の区分

| 検証方法 | 内容 | 主な対象章 |
|---|---|---|
| 性能テスト | 指定した負荷・データ量で応答時間・スループットを測定する | 5章 |
| 負荷テスト・耐久テスト | 上限負荷や長時間稼働時の挙動・劣化を確認する | 5章 |
| 障害テスト | 障害を擬似的に発生させ、切替・縮退・復旧を確認する | 4章 |
| バックアップ・リストアテスト | バックアップ取得とリストアを実施し、所要時間・復旧時点を確認する | 4章 |
| 運用テスト | 監視通知・ジョブ運用・運用手順が実施できることを確認する | 6章 |
| 移行リハーサル | 本番相当の手順・データ量で移行を試行する | 7章 |
| セキュリティテスト | 認証・認可・セッション・入力値検証の動作を確認する | 8章 |
| 脆弱性診断 | 診断ツールまたは診断者により脆弱性の有無を確認する | 8章 |
| 互換性・操作性テスト | 対応ブラウザ・デバイス・アクセシビリティ基準への適合を確認する | 9章 |
| 静的解析・コードレビュー | ソースコードを解析ツールまたはレビューで確認する | 6章、8章、10章 |
| 構成・設定レビュー | 構成・設定値・手順書の内容で確認する | 全章 |
| 運用時に測定 | リリース後の実運用で測定・評価する。検証環境で測定できない指標に限り使用する | 4章、5章、6章、8章、10章 |

### 3.3 記述上の規則

- 目標値または検証方法が空欄の要件は作らない。決められない場合は「未決」と記入し、14章に登録する。
- 応答時間は平均値ではなく95パーセンタイルで指定する。応答時間の計測区間は各要件の「要件内容」に記述する。
- 測定条件には、負荷・データ量・環境（12.1 の環境ID）の3点を含める。いずれかが不要な場合は「該当なし」と記入する。
- 開発・検証環境（ENV-01）で検証できない指標は、検証方法に「運用時に測定」と明記し、代替確認手段（構成・設定レビュー、ENV-01 での参考測定）を併記する。あわせて 12.3 に差異として登録する。
- 他章と同じ値を使う場合は値を一致させ、「根拠」に本書内の出典（章・ID）を記入する。
- 本書で用いる機能ID（FR-xxx）・画面ID（SCR-xxx）・利用者区分ID（ACT-xxx）は、MiniCommerce の機能・画面・利用者区分の識別子であり、本書では初出箇所で名称を併記する。
- 日時は日本時間（JST、Asia/Tokyo）、金額は整数の円で記述する。

### 6.3 ログ

アプリケーションログ（LOG-01〜LOG-03、LOG-06）は1つの JSON Lines 形式の出力として app の標準出力に出し、保管期間は90日とする。監査ログ（LOG-04）は DB に記録し1年保管する。注文状態履歴（LOG-07）はログではなく業務データとして DB に記録し、注文日から7年保管する。いずれのログにも、パスワード・認証トークン・メールアドレス・氏名・住所・電話番号を出力しない（NFR-SC-06）。
