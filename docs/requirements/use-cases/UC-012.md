## 1. 本書の目的と適用範囲



### 1.1 目的

管理者（EC運営担当）が、任意の購入者の出荷前（注文受付・支払済）の注文を取り消し、引き当てられていた在庫数量を全明細分だけ1回だけ在庫へ戻すことで、購入者からの依頼（本システム外で受付）や運営上の判断による取消を在庫と整合させて反映する。

対象範囲（原資料 In Scope）：

- 注文詳細（管理）（SCR-103）の「キャンセル」と確認ダイアログによるキャンセル（FR-045）
- 注文キャンセル（管理者）API（POST /api/admin/purchase-orders/{purchase_order_id}/cancel）によるキャンセル（FR-045）
- 状態 created→cancelled（ST-PO-03）・paid→cancelled（ST-PO-04）の遷移、キャンセル日時の記録、全明細の在庫戻し、注文状態履歴（actor_role=admin）の記録

対象外（原資料 Out of Scope）：

- 支払済注文の返金（EC運営担当が本システム外で5営業日以内に行う。FR-OUT-04）

## 3. 目的・開始条件



### 3.1 Goal

管理者（EC運営担当）が、任意の購入者の出荷前（注文受付・支払済）の注文を取り消し、引き当てられていた在庫数量を全明細分だけ1回だけ在庫へ戻すことで、購入者からの依頼（本システム外で受付）や運営上の判断による取消を在庫と整合させて反映する。


### 3.2 Trigger

EC運営担当が注文の取消を決めたとき（購入者からの取消依頼を本システム外で受けた場合を含む）に、注文詳細（管理）（SCR-103）で「キャンセル」を押す。API を利用する場合は、管理者が注文キャンセル（管理者）API を呼び出す。


### 3.3 Precondition

| ID | 前提条件 | 満たさない場合の扱い |
|---|---|---|
| PRE-UC-012-001 | 管理者（ロール admin）がログイン済みで、認証トークンまたはログインセッションが有効である。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-012-002 | 対象の注文が存在する（所有する購入者は問わない）。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-012-003 | キャンセルを完了するには、注文の状態が注文受付（created）または支払済（paid）である。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |

## 7. Postcondition



### 7.1 正常終了

- 注文の状態が cancelled で、cancelled_at に処理時刻（+09:00 付き）が記録されている。
- 注文の全明細の数量が、それぞれの在庫単位の在庫数量へ1回だけ加算されている。
- 注文状態履歴に from_status=created または paid、to_status=cancelled、actor_role=admin、actor_user_id＝操作した管理者の行が1件追加されている。
- 支払済注文の場合、paid_at と決済記録は変化していない。
- 購入者の注文詳細（SCR-010）にも状態「キャンセル済」と actor_role=admin の状態履歴が表示される。


### 7.2 失敗終了

- エラー時は、注文の状態・各日時・在庫数量・注文状態履歴・決済記録は一切変化しない。
- 同じ注文の在庫が2回以上戻されることはない。

## 9. Acceptance Criteria / 合否判定基準



### 9.1 AC-UC-012-001：管理者が購入者の注文受付の注文をキャンセルすると在庫が戻る

| 項目 | 内容 |
|---|---|
| Type | 機能 |
| 関連Requirement ID | FR-045 |
| 関連Flow | MAIN |
| 優先度 | 必須 |

#### Given

- 管理者X（admin-01@example.com、ロール admin）がログイン済み。
- 注文 PO-00000001：所有者 購入者A（buyer-a@example.com）、状態 created、明細 MUG-WHT-01（税抜単価2,500円）×2、小計5,000円、送料0円、消費税額500円、合計5,500円、cancelled_at=null。
- PO-00000001 の決済記録0件、注文状態履歴1件（なし→created）。

#### When

- 管理者Xが PO-00000001 に注文キャンセル（管理者）API を呼び出す。


#### Then

- status_history は2件で、2件目が from_status=created、to_status=cancelled、actor_role=admin、actor_user_id＝管理者XのID。
- 在庫単位 MUG-WHT-01 の在庫数量10。
- 決済記録0件のまま。注文の各金額・明細・配送先は変化しない。

- 各試行で、支払は次のどちらか一方となる。(a) キャンセルが先に確定した場合：HTTP 409、error.code=INVALID_STATUS_TRANSITION、error.context.current_status=cancelled。(b) 支払が先に確定した場合：HTTP 200、status=paid。
- (a) の試行：キャンセルの応答の payment_records は空配列、paid_at=null、status_history は2件（2件目 created→cancelled、actor_role=admin）。
- (b) の試行：キャンセルの応答の payment_records は result=approved・amount=5500 の1件で、DB の決済記録もこの1件のまま変化しない。paid_at は null でない。status_history は3件（2件目 created→paid、actor_role=buyer、3件目 paid→cancelled、actor_role=admin）。
- (a)(b) とも、試行後の注文の状態は cancelled、在庫単位 MUG-WHT-01 の在庫数量は試行開始時点から＋2 だけ増える。


#### 測定・許容条件

| 項目 | 内容 |
|---|---|
| 指標 | Then を満たした試行の数 |
| 目標値 | 10試行中10試行 |
| 測定条件 | 独立した条件指定は原資料に記載なし。Given / Whenにある条件を参照 |
| 許容範囲 | 0試行（1試行でも満たさなければ不合格） |
| 検証方法 | 並列に要求を送信できる HTTP クライアントで2要求を同時に送信し、各試行後に DB の注文・決済記録・注文状態履歴・在庫単位を確認する。(a)(b) のどちらが発生するかは合否に影響しない。 |


#### Pass / Fail Rule

| 判定 | 条件 |
|---|---|
| PASS | 10試行すべてで Then の全項目を満たす。 |
| FAIL | 1試行でも、キャンセルが 200 以外になる、支払が (a)(b) 以外の応答になる、試行後の状態が cancelled でない、(a) で決済記録が登録される、(b) で決済記録が変更・削除される、または在庫数量の増加が＋2 以外になる。 |
| BLOCKED | 2要求を同時に送信する手段が無い場合。 |


#### Evidence

- 並列送信ツールの実行結果、DB の注文・決済記録・注文状態履歴・在庫単位。
