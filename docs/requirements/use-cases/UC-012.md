## 1. 本書の目的と適用範囲



### 1.1 目的

管理者（EC運営担当）が、任意の購入者の出荷前（注文受付・支払済）の注文を取り消し、引き当てられていた在庫数量を全明細分だけ1回だけ在庫へ戻すことで、購入者からの依頼（本システム外で受付）や運営上の判断による取消を在庫と整合させて反映する。


### 1.2 適用範囲

| 区分 | 内容 |
|---|---|
| Use Case ID | UC-012 |
| 対象ユースケース | 注文をキャンセルする（管理者） |
| 対象リリース・範囲 | MiniCommerce 初期リリース |
| 本書で定義する | Goal、Actor、Trigger、Precondition、Flow、Postcondition、Business Rule、AC |
| 本書で定義しない | 実装方式、画面デザイン詳細、物理データ構造、API・ファイルの物理仕様 |

対象範囲：

- 注文詳細（管理）（SCR-103）の「キャンセル」と実行前の確認によるキャンセル（FR-045）
- 状態 注文受付→キャンセル済（ST-PO-03）・支払済→キャンセル済（ST-PO-04）の遷移、キャンセル日時の記録、全明細の在庫戻し、注文状態履歴（実行者の利用者区分 管理者）の記録
- キャンセルできない状態（出荷済／配達完了／キャンセル済）の拒否と、二重キャンセルの防止

対象外：

- 支払済注文の返金（EC運営担当が本システム外で5営業日以内に行う。FR-OUT-04）
- 購入者からのキャンセル依頼の受付（電話・メール。本システム外）
- 購入者自身によるキャンセル（UC-009）
- 出荷後の返品・明細単位の部分キャンセル（FR-OUT-04）
- キャンセルの通知メール（FR-OUT-08）

## 3. 目的・開始条件



### 3.1 Goal

管理者（EC運営担当）が、任意の購入者の出荷前（注文受付・支払済）の注文を取り消し、引き当てられていた在庫数量を全明細分だけ1回だけ在庫へ戻すことで、購入者からの依頼（本システム外で受付）や運営上の判断による取消を在庫と整合させて反映する。


### 3.2 Trigger

EC運営担当が注文の取消を決めたとき（購入者からの取消依頼を本システム外で受けた場合を含む）に、注文詳細（管理）（SCR-103）で「キャンセル」を操作する。管理者は同じ操作を Web API で要求することもできる。


### 3.3 Precondition

| ID | 前提条件 | 満たさない場合の扱い |
|---|---|---|
| PRE-UC-012-001 | 管理者がログイン済みで、ログイン状態が有効期間内である。 | 開始不可。未ログイン・ログイン状態の期限切れは EX-01、購入者によるログインは EX-02 |
| PRE-UC-012-002 | 対象の注文が存在する（所有する購入者は問わない）。 | キャンセルできない（EX-03） |
| PRE-UC-012-003 | キャンセルを完了するには、注文の状態が注文受付または支払済である。 | キャンセルを受け付けない（EX-04） |

## 7. Postcondition



### 7.1 正常終了

- 注文の状態がキャンセル済で、キャンセル日時に処理時刻（日本時間）が記録されている。
- 注文の全明細の数量が、それぞれの在庫単位の在庫数量へ1回だけ加算されている。
- 注文状態履歴に変更前状態 注文受付または支払済、変更後状態 キャンセル済、実行者の利用者区分 管理者、実行した利用者 操作した管理者の行が1件追加されている。
- 支払済注文の場合、支払日時と決済記録は変化していない。
- 購入者の注文詳細（SCR-010）にも状態「キャンセル済」と、実行者の利用者区分が管理者の状態履歴が表示される。


### 7.2 失敗終了

- エラー時は、注文の状態・各日時・在庫数量・注文状態履歴・決済記録は一切変化しない。
- 同じ注文の在庫が2回以上戻されることはない。

## 9. Acceptance Criteria / 合否判定基準



### 9.1 AC-UC-012-001：管理者が購入者の注文受付の注文をキャンセルすると在庫が戻る

| 項目 | 内容 |
|---|---|
| Type | 機能 |
| 関連Requirement ID | FR-045 |
| 関連Flow | MAIN |
| 優先度 | 必須 |

#### Given

- 管理者X（admin-01@example.com、利用者区分 管理者）がログイン済み。
- 注文 PO-00000001：所有者 購入者A（buyer-a@example.com）、状態 注文受付、明細 MUG-WHT-01（税抜単価2,500円）×2、小計5,000円、送料0円、消費税額500円、合計5,500円、キャンセル日時 値なし。
- PO-00000001 の決済記録0件、注文状態履歴1件（なし→注文受付）。
- 在庫単位 MUG-WHT-01 の在庫数量8。


#### When

### 9.11 AC-UC-012-011：管理者キャンセルと購入者の支払の同時実行は逐次実行と同じ結果になる

| 項目 | 内容 |
|---|---|
| Type | 機能 |
| 関連Requirement ID | FR-045, FR-031 |
| 関連Flow | EX-05 |
| 優先度 | 必須 |

#### Given

- 管理者Xと購入者Aがそれぞれログイン済み。
- 各試行の開始時点で、注文（所有者 購入者A、状態 注文受付、明細 MUG-WHT-01（税抜単価2,500円）×2、合計5,500円、支払日時 値なし、決済記録0件、注文状態履歴1件）を1件新たに用意し、在庫単位 MUG-WHT-01 の在庫数量を記録する。


#### When

- 管理者Xの注文キャンセル（管理者）と、購入者Aの支払（決済が承認される条件）を、その注文に対して同時に行う。これを注文を作り直して10試行行う。


#### Then

- 各試行で、管理者Xのキャンセルは完了する（状態 キャンセル済。出荷登録・配達完了登録・キャンセルはいずれも不可）。
- 各試行で、支払は次のどちらか一方となる。(a) キャンセルが先に確定した場合：支払は拒否され、現在の注文状態では支払えない旨と現在の状態（キャンセル済）が通知される。(b) 支払が先に確定した場合：支払が完了し、状態 支払済となる。
- (a) の試行：キャンセル後の注文詳細（管理）の決済記録は0件、支払日時 値なし、状態履歴は2件（2件目 注文受付→キャンセル済、実行者の利用者区分 管理者）。
- (b) の試行：キャンセル後の注文詳細（管理）の決済記録は決済結果 承認・決済金額5,500円の1件で、登録された決済記録もこの1件のまま変化しない。支払日時が記録されている。状態履歴は3件（2件目 注文受付→支払済、実行者の利用者区分 購入者、3件目 支払済→キャンセル済、実行者の利用者区分 管理者）。
- (a)(b) とも、試行後の注文の状態はキャンセル済、在庫単位 MUG-WHT-01 の在庫数量は試行開始時点から＋2 だけ増える。


#### 測定・許容条件

| 項目 | 内容 |
|---|---|
| 指標 | Then を満たした試行の数 |
| 目標値 | 10試行中10試行 |
| 測定条件 | 同一注文に管理者のキャンセルと購入者の支払を同時に行う。10試行 |
| 許容範囲 | 0試行（1試行でも満たさなければ不合格） |
| 検証方法 | キャンセルと支払を同時に行い、各試行後に注文・決済記録・注文状態履歴・在庫単位の在庫数量を確認する。(a)(b) のどちらが発生するかは合否に影響しない。 |


#### Pass / Fail Rule

| 判定 | 条件 |
|---|---|
| PASS | 10試行すべてで Then の全項目を満たす。 |
| FAIL | 1試行でも、キャンセルが完了しない、支払が (a)(b) 以外の結果になる、試行後の状態がキャンセル済でない、(a) で決済記録が登録される、(b) で決済記録が変更・削除される、または在庫数量の増加が＋2 以外になる。 |
| BLOCKED | 2件の要求を同時に行う手段が無い場合。 |


#### Evidence

- 各試行で通知された操作結果、登録された注文・決済記録・注文状態履歴の内容、在庫単位の在庫数量。
