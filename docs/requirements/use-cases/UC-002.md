## 1. 本書の目的と適用範囲



### 1.1 目的

会員登録済みの購入者、および管理者が、メールアドレスとパスワードで本人であることを示してログインし、利用者区分（購入者／管理者）に応じた機能を利用できる状態になる。利用後はログアウトして、使っていた認証トークン・ログインセッションを無効にする。


### 1.2 適用範囲

| 区分 | 内容 |
|---|---|
| Use Case ID | UC-002 |
| 対象ユースケース | ログイン・ログアウトする |
| 対象リリース・範囲 | MiniCommerce 初期リリース |
| 本書で定義する | Goal、Actor、Trigger、Precondition、Flow、Postcondition、Business Rule、AC |

対象範囲（原資料 In Scope）：

- ログイン画面（SCR-004）からのログインと、Web API（POST /api/auth/login）によるログイン（FR-002）
- 認証トークン（有効期間：発行から24時間）の発行と、画面のログインセッション（無操作30分で切断）の開始
- ログイン後の遷移（購入者は商品一覧 SCR-001、管理者は注文一覧 SCR-102。認証が必要な画面から誘導された場合は元の画面）
- ログアウト（FR-003、POST /api/auth/logout）による認証トークンの無効化と画面セッションの終了
- ログイン利用者情報照会（FR-004、GET /api/auth/me）
- 多重ログイン、認証エラー（未ログイン・ログアウト済・有効期間経過・セッション切断）の扱い
- ログイン成功・失敗、ログアウトの監査ログ記録

対象外（原資料 Out of Scope）：

- 会員登録（UC-001）
- 管理者アカウントの作成（UC-013）
- 会員情報の変更、パスワード再設定、退会（FR-OUT-09）
- 認証失敗時のアカウントロック、ログイン試行回数制限（FR-OUT-11）
- ログインに関するメール通知（FR-OUT-08）
- 監査ログの照会機能（本リリースでは提供しない）

## 3. 目的・開始条件



### 3.1 Goal

会員登録済みの購入者、および管理者が、メールアドレスとパスワードで本人であることを示してログインし、利用者区分（購入者／管理者）に応じた機能を利用できる状態になる。利用後はログアウトして、使っていた認証トークン・ログインセッションを無効にする。


### 3.2 Trigger

来訪者が共通ヘッダーのログインを選択してログイン画面（SCR-004）を表示し、ログインを実行したとき。または、未ログインの来訪者が認証を必要とする画面を要求して SCR-004 へ誘導されたとき。Web API では POST /api/auth/login の要求を受け付けたとき。ログアウトは、ログイン中の利用者が共通ヘッダーのログアウトを選択したとき、または POST /api/auth/logout の要求を受け付けたとき。


### 3.3 Precondition

| ID | 前提条件 | 満たさない場合の扱い |
|---|---|---|
| PRE-UC-002-001 | ログインする利用者（購入者または管理者）が利用者（User）として登録済みである（購入者は UC-001 または UC-013、管理者は UC-013 で登録）。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-002-002 | ログアウト（FR-003）・ログイン利用者情報照会（FR-004）は、有効な認証トークン（画面ではログインセッション）を持つ利用者が行う。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-002-003 | MiniCommerce が稼働している（計画停止中でない）。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |


## 4. 基本フロー

| Step | Actor / System | 操作・振る舞い | 結果・状態 |
|---|---|---|---|
| 1 | ACT-001 来訪者 | 共通ヘッダーのログインを選択する | ログイン画面（SCR-004）にメールアドレス・パスワードの入力欄が表示される |
| 2 | ACT-001 来訪者 | メールアドレス（email）とパスワード（password）を入力し、ログインを実行する（FR-002） | ログイン要求が送信される |
| 3 | System | email・password が未入力でないことを確認し、email の前後空白を除去して英小文字に正規化する | 正規化後の email で照合する |
| 4 | System | 正規化後の email の利用者が存在し、password が保存済みのハッシュ値と一致することを確認する | 認証に成功する |
| 5 | System | 認証トークン（有効期間：発行から24時間）を発行し、画面ではログインセッション（無操作30分で切断）を開始する。監査ログに login_success（user_id）を記録する | 利用者は ACT-002 購入者として認証済みとなる |
| 6 | System | API は HTTP 200 で token、expires_at（発行から24時間後、ISO 8601、+09:00 付き）、user（user_id、email、full_name、role＝buyer）を返す。画面は商品一覧（SCR-001）へ遷移し、共通ヘッダーに氏名とログアウトを表示する | 購入者向けの機能（UC-004〜UC-009）が利用できる |
| 7 | ACT-002 購入者 | ログイン利用者情報を照会する（FR-004、GET /api/auth/me） | 照会要求が送信される |
| 8 | System | HTTP 200 で自分の user_id、email、full_name、role を返す | 状態は変化しない |
| 9 | ACT-002 購入者 | 共通ヘッダーのログアウトを選択する（FR-003、POST /api/auth/logout） | ログアウト要求が送信される |
| 10 | System | 要求に使われた認証トークンを無効化し、画面のログインセッションを終了する。監査ログに logout（user_id）を記録する。API は HTTP 204 を返し、画面は商品一覧（SCR-001）へ遷移して共通ヘッダーにログインを表示する | 利用者は ACT-001 来訪者の状態に戻る。無効化したトークンでの要求は AUTHENTICATION_REQUIRED となる |

## 7. Postcondition



### 7.1 正常終了

- ログイン後：認証トークンが発行され、現在時刻が expires_at（発行から24時間後）より前の間だけ有効である（expires_at ちょうど以降は無効）。画面ではログインセッションが開始され、購入者は SCR-001、管理者は SCR-102（誘導された場合は元の画面）が表示されている。
- ログイン後：監査ログに login_success（user_id、result＝success）が1件記録されている。
- ログアウト後：要求に使われた認証トークンは無効で、以後の要求は AUTHENTICATION_REQUIRED（HTTP 401）となる。同じ利用者の他の認証トークンは有効なままである。画面は SCR-001 が未ログインの表示で表示されている。
- ログアウト後：監査ログに logout（user_id、result＝success）が1件記録されている。


### 7.2 失敗終了

- ログイン失敗時：認証トークンは発行されず、ログインセッションは開始されない。利用者（User）の内容は変化しない。
- 認証失敗（INVALID_CREDENTIALS）時：監査ログに login_failure（result＝failure）が1件記録されている。
- ログアウト失敗時：認証トークンの状態は操作前のままである。
- いずれの場合も、パスワード・メールアドレス・認証トークン・氏名はアプリケーションログ・監査ログに出力されない。

### 9.20 AC-UC-002-020：認証トークンは推測困難な乱数で発行される

| 項目 | 内容 |
|---|---|
| Type | セキュリティ |
| 関連Requirement ID | FR-002, NFR-SC-08 |
| 関連Flow | MAIN |
| 優先度 | 必須 |

#### Given

- 購入者 A が登録済みである。


#### When

- POST /api/auth/login に購入者 A の email・password を100回送信し、発行された token を収集する。
- 認証トークンの生成処理の実装を確認する。


#### Then

- 100回とも HTTP 200 で、収集した100件の token に重複がない。
- 生成処理が暗号論的擬似乱数生成器を用い、128ビット以上の乱数から token を生成している。


#### 測定・許容条件

| 項目 | 内容 |

| 指標 | 100件の token の重複件数、および token の生成に用いる乱数のビット数 |
| 目標値 | 重複0件、乱数128ビット以上 |
| 測定条件 | 独立した条件指定は原資料に記載なし。Given / Whenにある条件を参照 |
| 許容範囲 | 許容差なし |
| 検証方法 | 収集した token の重複を集計し、生成処理のソースコードで乱数生成器と乱数のビット数を確認する |


#### Pass / Fail Rule

| 判定 | 条件 |
|---|---|
| PASS | Then の全項目を満たす。 |
| FAIL | 重複が1件以上ある、または乱数のビット数が128ビット未満、または暗号論的擬似乱数生成器を用いていない。 |
| BLOCKED | 生成処理のソースコードを確認できない。 |


#### Evidence

- 100件の token の重複集計結果、生成処理のソースコードの該当箇所
