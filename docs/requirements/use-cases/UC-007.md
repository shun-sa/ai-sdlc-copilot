## 1. 本書の目的と適用範囲



### 1.1 目的

購入者が、自分の注文受付（created）状態の注文について、注文の合計金額を模擬決済で支払い、注文を支払済（paid）にする。支払の結果（承認・否認・連携エラー）は決済記録として残り、否認・連携エラーの場合は注文受付のまま再度支払える。


### 1.2 適用範囲

| 区分 | 内容 |
|---|---|
| Use Case ID | UC-007 |
| 対象ユースケース | 注文の代金を支払う（模擬決済） |
| 対象リリース・範囲 | MiniCommerce 初期リリース |
| 本書で定義する | Goal、Actor、Trigger、Precondition、Flow、Postcondition、Business Rule、AC |
| 本書で定義しない | 新たな実装方式の決定。受領済みのAPI・画面条件は要求根拠として維持 |

対象範囲（原資料 In Scope）：

- 支払画面（SCR-008）での注文番号・合計金額の表示（FR-033）と、模擬決済の結果（承認／否認）を選択した支払（FR-031）
- 支払 API（POST /api/purchase-orders/{purchase_order_id}/pay）による支払（FR-031）
- 決済サービス（模擬）への決済要求（注文番号・決済金額・通貨 JPY・模擬決済指示）と、承認・否認・応答なし（10秒超過）・応答不正の各結果の処理
- 決済記録（approved／declined／error）の登録、注文状態の created→paid の遷移（ST-PO-02）、支払日時と注文状態履歴の記録
- 同一注文への同時支払の制御

対象外（原資料 Out of Scope）：

- 実在の決済サービスとの連携（FR-OUT-01）
- 返金（支払済注文のキャンセル時の返金は本システム外で行う。FR-OUT-04）
- 注文確定（UC-006）、注文のキャンセル（UC-009、UC-012）
- 未払い注文の自動キャンセル（FR-OUT-12）
- 支払完了の通知メール（FR-OUT-08）
- 決済要求の自動再送（二重決済防止のため行わない）

## 3. 目的・開始条件



### 3.1 Goal

購入者が、自分の注文受付（created）状態の注文について、注文の合計金額を模擬決済で支払い、注文を支払済（paid）にする。支払の結果（承認・否認・連携エラー）は決済記録として残り、否認・連携エラーの場合は注文受付のまま再度支払える。


### 3.2 Trigger

購入者が、注文完了画面（SCR-007）の「支払へ進む」または注文詳細画面（SCR-010）の「支払う」を押し、支払画面（SCR-008）で「支払う」を押す。API を利用する場合は、購入者が支払 API を呼び出す。


### 3.3 Precondition

| ID | 前提条件 | 満たさない場合の扱い |
|---|---|---|
| PRE-UC-007-001 | 購入者（ロール buyer）がログイン済みで、認証トークン（発行から24時間以内でログアウトしていない）またはログインセッション（無操作30分以内）が有効である。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-007-002 | 支払対象の注文が、ログイン中の購入者が注文確定（UC-006、FR-030）した注文として存在する。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-007-003 | 支払を完了するには、注文の状態が注文受付（created）である。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-007-004 | 決済サービス（模擬）が本システム内の機能として稼働し、外部ネットワークに接続せずに1秒以内に応答する。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |


## 4. 基本フロー

| Step | Actor / System | 操作・振る舞い | 結果・状態 |
|---|---|---|---|
| 1 | 購入者 | 注文詳細画面（SCR-010）で、can_pay=true のときに表示される「支払う」を押す | 注文 created |
| 2 | System | 支払画面（SCR-008）に注文番号・合計金額（例「5,500円」）と「模擬決済の結果」の選択欄（承認／否認、初期選択は承認）を表示する（FR-033） | 変更なし |
| 3 | 購入者 | 「模擬決済の結果」を承認のまま「支払う」を押す | 「支払う」は処理完了まで再押下できない |
| 4 | System | ①認証 →②権限（購入者であること）→③入力（mock_result=approve）→④注文の存在と所有 →⑤状態が created であること、の順に判定する（FR-031） | 変更なし |
| 5 | System | 決済サービス（模擬）へ注文番号・決済金額（注文の合計金額）・通貨 JPY・模擬決済指示 approve を送り、応答を最大10秒待つ（FR-031） | 変更なし |
| 6 | 決済サービス（模擬） | 結果 approved、取引参照番号（"MOCK-" に続く英数字16文字）、処理日時を1秒以内に返す | 変更なし |
| 7 | System | 決済記録（result=approved、取引参照番号、金額＝合計金額、処理日時）を登録し、注文状態を paid、支払日時（paid_at）を処理時刻で記録し、注文状態履歴（from_status=created、to_status=paid、actor_role=buyer、actor_user_id＝購入者）を1件記録する。これらを一括で反映する（FR-031） | 注文 paid（ST-PO-02）、approved の決済記録1件、在庫数量は変化しない |
| 8 | System | 200 と注文詳細表現（status=paid、can_pay=false、can_cancel=true）を返す。画面は注文詳細画面（SCR-010）へ遷移し、画面上部のメッセージ領域に支払完了メッセージを表示する | 注文 paid |

| 2 | System | 支払が先に確定した場合、後着のキャンセルは支払済からのキャンセルとして成功する（在庫戻しを行い、決済記録は変更しない）（FR-031, FR-034, FR-045） | 注文 cancelled、approved の決済記録1件はそのまま、注文状態履歴は created→paid、paid→cancelled の2件が追加、在庫数量は全明細の数量分戻る |


## 7. Postcondition



### 7.1 正常終了

- 注文の状態が paid で、paid_at に処理時刻（+09:00 付き）が記録されている。
- 当該注文の決済記録に result=approved が1件あり、取引参照番号は "MOCK-" に続く英数字16文字、金額は注文の合計金額と一致する。
- 注文状態履歴に from_status=created、to_status=paid、actor_role=buyer、actor_user_id＝支払った購入者の行が1件追加されている。
- 在庫数量、注文の各金額・明細・配送先・注文日時は変化していない。
- 注文詳細で can_pay=false、can_cancel=true となる。


### 7.2 失敗終了

- 否認・連携エラーの場合：注文の状態は created、paid_at は null、注文状態履歴は増えない。決済記録に declined または error が1件追加される以外の変更はない。購入者は再度支払える。
- 認証・権限・入力・対象なし・状態不正のエラーの場合：注文・決済記録・注文状態履歴・在庫数量は一切変化せず、決済サービス（模擬）へ要求しない。
- いずれの場合も、1注文あたりの approved の決済記録は最大1件である。

### 9.19 AC-UC-007-019：同一注文への支払とキャンセルの同時実行は、逐次実行したいずれかの順序の結果と一致する

| 項目 | 内容 |
|---|---|
| Type | データ |
| 関連Requirement ID | FR-031, FR-034 |
| 関連Flow | EX-10 |
| 優先度 | 必須 |

#### Given

- 購入者Aがログイン済み。
- 各試行の開始時点で、注文（所有者 購入者A、状態 created、明細 MUG-WHT-01×2、合計5,500円、決済記録0件、注文状態履歴1件）を1件新たに用意する。在庫単位 MUG-WHT-01 の在庫数量は各試行の開始時点の値を記録する。


#### When

- 購入者Aの認証トークンで、その注文に mock_result="approve" の支払要求とキャンセル要求（FR-034）を同時に送信する（2要求の送信開始時刻の差は10ミリ秒以内）。これを注文を作り直して10試行行う。


#### Then

- 各試行で、キャンセル要求は HTTP 200（status=cancelled）。
- 各試行で、支払要求の結果は次の (a)(b) のいずれかで、それぞれの条件を満たす。(a) HTTP 409、error.code=INVALID_STATUS_TRANSITION、error.context.current_status=cancelled：決済記録0件、注文状態履歴2件（created→cancelled）、決済サービス（模擬）は当該注文の決済要求を受けていない。(b) HTTP 200（status=paid）：決済記録は approved 1件のみ、注文状態履歴3件（created→paid、paid→cancelled の順）。
- 各試行で、注文の最終状態は cancelled、在庫単位 MUG-WHT-01 の在庫数量は試行開始時点の値＋2（在庫戻しは1回だけ）。


#### 測定・許容条件

| 項目 | 内容 |
|---|---|
| 指標 | Then を満たした試行の数（あわせて (a)(b) それぞれの発生件数を記録する） |
| 目標値 | 10試行中10試行 |
| 測定条件 | 独立した条件指定は原資料に記載なし。Given / Whenにある条件を参照 |
| 許容範囲 | 0試行（1試行でも満たさなければ不合格） |
| 検証方法 | 並列に要求を送信できる HTTP クライアントで2要求を同時に送信し、各試行後に DB の注文・決済記録・注文状態履歴・在庫単位と、決済サービス（模擬）の受信記録を確認する。 |


#### Pass / Fail Rule

| 判定 | 条件 |
|---|---|
| PASS | 10試行すべてで Then の全項目を満たす。 |
| FAIL | 1試行でも、キャンセルが 200 以外になる、支払の結果が (a)(b) のいずれにも一致しない（(a) で決済記録が登録される、(b) で approved が2件以上になる場合を含む）、在庫数量が試行開始時点の値＋2 でない、または最終状態が cancelled でない。 |
| BLOCKED | 2要求を同時に送信する手段が無い場合。 |


#### Evidence

- 並列送信ツールの実行結果（各要求のステータス・本文・送信時刻）、決済サービス（模擬）の受信記録、DB の注文・決済記録・注文状態履歴・在庫単位。
