## 1. 本書の目的と適用範囲



### 1.1 目的

購入者が、問い合わせをせずに自分の注文の一覧と各注文の状況（状態・支払日時・出荷日時・配送伝票番号・配達完了日時・キャンセル日時）、金額の内訳、明細、配送先、状態の変更経過を確認でき、状態に応じて支払・キャンセルへ進める。


### 1.2 適用範囲

| 区分 | 内容 |
|---|---|
| Use Case ID | UC-008 |
| 対象ユースケース | 注文履歴・注文状況を確認する |
| 対象リリース・範囲 | MiniCommerce 初期リリース |
| 本書で定義する | Goal、Actor、Trigger、Precondition、Flow、Postcondition、Business Rule、AC |
| 本書で定義しない | 新たな実装方式の決定。受領済みのAPI・画面条件は要求根拠として維持 |

対象範囲（原資料 In Scope）：

- 注文履歴一覧（SCR-009、FR-032、GET /api/purchase-orders）：自分の注文のみ、注文日時降順、1ページ20件
- 注文詳細（SCR-010、FR-033、GET /api/purchase-orders/{purchase_order_id}）：金額・明細スナップショット・クーポン・配送先・各日時・配送伝票番号・状態履歴（変更日時昇順）、can_pay・can_cancel
- 注文詳細から支払（UC-007）・キャンセル（UC-009）への導線の表示

対象外（原資料 Out of Scope）：

- 支払の実行（UC-007）、キャンセルの実行（UC-009）
- 決済記録の参照（購入者は参照できない）
- 他の購入者の注文の参照、管理者による全注文の検索（UC-011）
- 帳票・ファイル出力（FR-OUT-15）、注文状況の通知メール（FR-OUT-08）
- 注文履歴の検索条件の指定（本UCの一覧はページ指定のみ）

## 3. 目的・開始条件



### 3.1 Goal

購入者が、問い合わせをせずに自分の注文の一覧と各注文の状況（状態・支払日時・出荷日時・配送伝票番号・配達完了日時・キャンセル日時）、金額の内訳、明細、配送先、状態の変更経過を確認でき、状態に応じて支払・キャンセルへ進める。


### 3.2 Trigger

購入者が共通ヘッダーの「注文履歴」を押す、または注文完了画面（SCR-007）の「注文詳細を見る」を押す。API を利用する場合は、購入者が注文履歴一覧 API または注文詳細 API を呼び出す。


### 3.3 Precondition

| ID | 前提条件 | 満たさない場合の扱い |
|---|---|---|
| PRE-UC-008-001 | 購入者（ロール buyer）がログイン済みで、認証トークンまたはログインセッションが有効である。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |
| PRE-UC-008-002 | 注文詳細を表示する場合、対象の注文がログイン中の購入者の注文として存在する。 | 原資料では前提ごとの個別対応は未記載。機能要件と6章の例外フローを参照 |


## 4. 基本フロー

| Step | Actor / System | 操作・振る舞い | 結果・状態 |
|---|---|---|---|
| 1 | 購入者 | 共通ヘッダーの「注文履歴」を押す | 変更なし |
| 2 | System | 認証・権限（購入者）を判定し、注文履歴一覧（SCR-009、FR-032）に自分の注文だけを注文日時降順（同値は注文ID降順）で1ページ20件表示する。各行は注文番号・注文日時（YYYY/MM/DD HH:MM）・状態の表示名・合計（例「5,500円」）・合計点数 | 変更なし（照会のみ） |
| 3 | 購入者 | 一覧から注文を1件選ぶ | 変更なし |
| 4 | System | 注文の存在と所有を判定し、注文詳細（SCR-010、FR-033）に注文番号・状態・注文日時・支払日時・出荷日時・配達完了日時・キャンセル日時（未発生は表示なし）・配送伝票番号・明細（注文確定時のスナップショット。注文明細ID昇順）・クーポン・金額内訳（小計・割引額・割引後小計・送料・消費税額・合計）・配送先・状態履歴（変更日時昇順）を表示する | 変更なし |

| 6 | 購入者 | 注文の状況を確認する | 変更なし |

## 7. Postcondition



### 7.1 正常終了

- 購入者が自分の注文だけを、注文日時降順・1ページ20件で確認できている。
- 注文詳細で、注文確定時点の明細・金額、配送先、現在の状態と各日時、配送伝票番号、状態履歴（変更日時昇順）、can_pay・can_cancel が状態に一致して表示されている。
- 照会のみであり、注文・在庫・決済記録・注文状態履歴は変化していない。


### 7.2 失敗終了

- エラー時も注文・在庫・決済記録・注文状態履歴は変化しない。
- 他の購入者の注文の存在有無・内容は応答・画面に現れない。

## 9. Acceptance Criteria / 合否判定基準



### 9.1 AC-UC-008-001：自分の注文だけが注文日時降順で一覧表示される

| 項目 | 内容 |
|---|---|
| Type | 機能 |
| 関連Requirement ID | FR-032, NFR-SC-03 |
| 関連Flow | MAIN |
| 優先度 | 必須 |

#### Given

- 購入者A（buyer-a@example.com、ロール buyer）がログイン済み。
- 購入者Aの注文：PO-00000001（ordered_at=2027-04-01T10:00:00+09:00、状態 created、合計5,500円、明細の数量合計2）、PO-00000003（ordered_at=2027-04-02T09:00:00+09:00、状態 paid、合計6,048円、数量合計1）、PO-00000004（ordered_at=2027-04-03T15:30:00+09:00、状態 shipped、合計6,044円、数量合計3）。
- 購入者B（buyer-b@example.com）の注文：PO-00000002（ordered_at=2027-04-01T12:00:00+09:00、状態 created、合計3,300円）。


#### When

- 購入者Aが page を指定せずに注文履歴一覧 API を呼び出す。


#### Then

- HTTP 200。results は3件で、順に PO-00000004、PO-00000003、PO-00000001。PO-00000002 は含まれない。
- 各要素の項目は purchase_order_id, order_number, ordered_at, status, total, total_quantity。PO-00000004 の要素は ordered_at=2027-04-03T15:30:00+09:00、status=shipped、total=6044、total_quantity=3。
- page=1、page_size=20、total_count=3、total_pages=1。


#### 測定・許容条件

| 項目 | 内容 |
|---|---|
| 指標 | None |
| 目標値 | None |
| 測定条件 | 独立した条件指定は原資料に記載なし。Given / Whenにある条件を参照 |
| 許容範囲 | None |
| 検証方法 | None |


#### Pass / Fail Rule

| 判定 | 条件 |
|---|---|
| PASS | Then の全項目を満たす。 |
| FAIL | 他の購入者の注文が含まれる、並び順・件数・項目値が Then と一致しない。 |
| BLOCKED | 2名の試験用購入者と注文を用意できない場合。 |


#### Evidence

- 注文履歴一覧 API のレスポンス、DB の注文。
