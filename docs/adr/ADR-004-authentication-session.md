# ADR-004 認証方式にサーバーサイドセッションを採用する

## Status

Accepted

## Related Requirements

- FR-002
- FR-007
- FR-008
- FR-009
- NFR-SEC-002
- NFR-SEC-006

## Context

会員機能はログインを必須とし（FR-002）、未認証アクセスを許可しない（NFR-SEC-002）。
認証失敗時にアカウント存在可否を推測させない（NFR-SEC-006/ERR-002）要件がある。
サーバーレンダリングWebで一般的な認証保持方式を確定する必要がある。

## Decision

サーバーサイドセッション（サーバー保持のセッションID、HttpOnly/Secure/SameSite Cookie）を採用する。
状態変更操作（FR-007/FR-008/FR-009等のPOST）はCSRFトークン検証等のCSRF対策を必須とする。
セッションIDはCSPRNGで生成し、ログイン成功時に再生成する。
セッション署名鍵/シークレットは設定注入で供給し、コード/テストへ埋め込まない。
ログイン失敗は原因を区別しない汎用メッセージを返す。

## Alternatives

- サーバーサイドセッション（採用）
  - Web UIに適合し失効・無効化制御が容易でNFR-SEC-002に適合
- JWT（ステートレストークン）（不採用）
  - 即時失効が難しくWeb画面主体の本要件に優位性がない
- Basic認証（不採用）
  - セッション制御・ログアウト・UXが不十分

## Consequences

- メリット: 認証状態の失効管理が容易でCookie保護を標準適用できる
- デメリット: セッションストアの用意が必要
- 後続工程: 要認証機能はセッション検証を前提に実装・テストする

## AI Guardrails

- 認証失敗理由でアカウント存在有無を推測可能にしてはならない（NFR-SEC-006）
- Session CookieのHttpOnly/Secure/SameSite属性と状態変更操作のCSRF対策を省略してはならない
- セッションIDはCSPRNGで生成しログイン成功時に再生成し、署名鍵/シークレット・ストア接続情報は設定注入とし、コード/テストデータへハードコードしてはならない
