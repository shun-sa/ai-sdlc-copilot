## 3. 背景

### 3.1 判断が必要な理由

要件は結果（在庫数量が0未満にならない、引当合計が初期在庫以下、承認済み決済は1注文につき最大1件、同一カートの二重送信で作成される注文は1件）だけを定め、排他の実現方式を定めていない。さらに「参照した時点から更新する時点までの間の他の要求による更新は検出しない」と明記されているため、どの時点でどの行をどう保護するかを決めないと、同一在庫単位への10並列の注文確定（NFR-PF-07）で結果が一意にならない。

### 3.2 判断時の制約

- 同時実行の競合に専用のエラーコードを設けず、既存の業務エラー（INSUFFICIENT_STOCK・INVALID_STATUS_TRANSITION・CART_EMPTY・EMAIL_ALREADY_REGISTERED）で返す（提供済みAPI契約 6.2）。
- 更新を伴う機能は全成功か無変更のどちらかとする。ただし支払否認・外部連携エラーの決済記録と失敗時の監査ログは残す。
- 更新検出（参照時点からの変化の検出）を行う方式は採用できない。
- 更新系APIの応答時間は95パーセンタイルで2.0秒以内（NFR-PF-02）。
- DBは PostgreSQL 16（Docker Compose の db サービス）であり、追加のミドルウェア（分散ロック基盤等）を導入しない。

### 4.3 決定内容

- 隔離水準は PostgreSQL 既定の READ COMMITTED を用い、更新系の処理単位を1つのDBトランザクション（`transaction.atomic`）に収める。
- トランザクション内で、更新対象の行を `select_for_update()`（待機あり。`nowait`・`skip_locked` は用いない）で取得してから判定する。ロック取得順序は「在庫単位（識別子の昇順）→ カート → 注文」に固定する。注文単位の更新（支払・キャンセル・出荷・配達完了）は対象注文行を先にロックする。
- 注文確定（FR-030）：カート行と注文対象の全在庫単位行をロックしたうえで、数量上限・商品の公開状態・クーポン条件・在庫数量を再判定し、全明細の在庫減算・注文作成・状態履歴記録・カート状態更新を同一トランザクションで確定する。不足がある場合は不足する全件を `INSUFFICIENT_STOCK` のcontextへ列挙してロールバックする。二重送信の後着は、先着がカートを注文済へ変更済みであるため `CART_EMPTY` となる。
- 支払（FR-031）：注文行をロックして状態を再判定し、注文受付以外は `INVALID_STATUS_TRANSITION` とする。模擬決済の呼出しはロックを保持しない区間で行い（ADDR-009）、結果受領後に注文更新と決済記録登録を同一トランザクションで確定する。
- キャンセル・出荷・配達完了（FR-034・FR-043〜FR-045）：注文行と戻し対象の在庫単位行をロックして状態を再判定し、状態更新・在庫戻し・状態履歴記録を同一トランザクションで確定する。
- 会員登録（FR-001）と業務キーの重複は、行ロックではなくDBの一意制約で解決する。サービス層がDBの整合性例外（一意制約違反）を捕捉して対応する業務例外（メールアドレス重複は `EMAIL_ALREADY_REGISTERED`）へ変換して送出し、エラーコードへの写像は ADDR-011 の「制約名→業務例外」の対応表に従う。取りこぼした整合性例外も ADDR-011 の共通ハンドラの整合性例外分岐で同じ業務エラーへ写像されるため、`INTERNAL_ERROR` にはならない。

### 4.4 決定理由

更新検出を行わないという制約（DC-002）のもとで DC-001 を満たすには、判定と更新の間に他要求が割り込まないことを保証する必要があり、行ロックによる悲観的制御が唯一整合する。楽観的制御（OPT-002）は更新検出そのものであり要件と反する。制約と条件付きUPDATEのみ（OPT-003）は、不足在庫の全件列挙と「全成功か無変更」を両立できない。ロック順序を在庫単位の識別子昇順に固定することでデッドロックを構造的に避け、ロック区間から外部呼出しを除くことで応答時間目標（DC-005）への影響を抑える。
