## 3. 背景

### 3.1 判断が必要な理由

FR-031 と IF-01 は要求・応答の項目、結果（承認・否認・応答なし）、タイムアウト10秒・自動再送なしを定め、模擬決済指示が入力項目であることも定めている。一方で、模擬機能を app 内のどの層へ置くか、注文処理からどう呼び出すか、将来の実決済サービスへ差し替える範囲をどう区切るかは定めていない。NFR-PF-17 は「決済連携部分を分離すること」を求めるが手段を定めていないため、分離境界を設計で確定する必要がある。

### 3.2 判断時の制約

- 実在の決済サービス・外部APIへ接続する処理を実装しない（外部ネットワークへ接続しない）。
- 決済要求に個人情報を含めない（注文番号・決済金額・通貨・模擬決済指示のみ）。
- 自動再送を行わない（二重決済防止）。応答待ちは最大10秒、模擬機能は1秒以内に応答する。
- 否認・外部連携エラーでも決済記録を登録し、注文は注文受付のまま維持する。
- 接続先・実装の選択を利用者入力で変更できないようにする。
- モジュール配置は ADDR-001 の分割（payments／orders）に従う。

### 4.3 決定内容

- 配置：`app/payments/` に次を置く。(1) 決済要求・決済結果のデータ構造、(2) 決済ゲートウェイのインターフェース（`authorize(order_number, amount, currency, mock_result)` が決済結果を返す）、(3) 模擬実装（承認時は取引参照番号「MOCK-」＋英数字16桁と処理日時、否認時は否認理由コードと処理日時を1秒以内に返す）、(4) タイムアウト・応答不正を表す例外。
- 解決方法：使用する実装は設定値（環境変数で上書き可能な設定キー）で指定し、呼出し元はファクトリ経由で取得する。利用者入力・要求本文で実装や接続先を切り替えない。
- 呼出し：支払処理（`orders` の services）はインターフェース経由で同期呼出しし、応答待ちは最大10秒、自動再送を行わない。10秒超過・応答不正は外部連携エラーとして扱う。
- トランザクション境界：決済要求の送信と応答待ちはDBトランザクションの外（行ロックを保持しない区間）で行う。結果を受け取った後、注文行をロックし直して状態を再判定したうえで、決済記録の登録と注文更新・状態履歴記録を同一トランザクションで確定する。否認・外部連携エラーのときは決済記録のみを別トランザクションで確定する。
- 入力の受け渡し：模擬決済指示は FR-031 の入力項目（省略時は承認）として受け取り、インターフェースの引数として渡す。テスト専用の設定・環境変数で結果を切り替える仕組みは設けない。
- 決済要求には注文番号・決済金額・通貨・模擬決済指示のみを渡し、購入者の個人情報を渡さない。

### 4.4 決定理由

NFR-PF-17 の「分離」を実装上で検証可能にするには、注文処理が模擬実装へ直接依存しない形（インターフェースと設定による解決）が必要である。OPT-002 は分離要件を満たさず、OPT-003 は app・db のみという構成制約に反する。応答待ち10秒を行ロック区間の外へ出すのは、ロック保持時間が更新系の応答時間（DC-005）と他要求の待ちへ直結するためであり、結果受領後に状態を再判定することで「承認済み決済は1注文につき最大1件」を保てる。
