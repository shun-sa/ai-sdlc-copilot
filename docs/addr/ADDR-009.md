## 3. 背景

### 3.1 判断が必要な理由

IF-01 は送受信データ・例外時の振る舞い・整合性（二重決済防止）を定めるが、模擬機能をどこに置き、どの境界で呼び出し、応答待ち10秒をどう制御するかは未提供である。境界の置き方によって、実決済サービスへの差替え時の影響範囲（NFR-PF-17）と、タイムアウト・応答不正の検出可否（IF-01-EXC-02〜04）が変わるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- 決済サービス（模擬）は本システム内の機能として実装し、外部ネットワークへ接続しない（Steering 10章、NFR-EN-05、11章）。
- 方式は同期の要求・応答で、1回の要求で1注文の支払1回分（IF-01-PRT-01、IF-01-PRT-04）。
- 応答待ちは最大10秒、自動再送なし（IF-01-PRF-05、IF-01-EXC-02）。
- 承認時の反映（決済記録・注文状態・支払日時・状態履歴）は一括確定（IF-01-CON-03）。
- 1注文につき承認済みの決済記録は最大1件（IF-01-CON-01）。
- カード番号を入力・保存・送信しない（NFR-LG-05）。

### 4.3 決定内容

- shop/payments モジュールに決済ゲートウェイの境界を定義する。要求データは IF-01-DAT-01〜04（注文番号、決済金額、通貨 JPY、模擬決済指示）だけを持つ構造、応答データは IF-01-DAT-05〜08（結果、取引参照番号、否認理由コード、処理日時）だけを持つ構造とし、注文・カート・在庫のモデルオブジェクトを渡さない。
- 模擬実装（MockPaymentGateway）は payments 内に置き、模擬決済指示が approve なら承認、decline なら否認を返す。承認時の取引参照番号は MOCK- ＋英数字16桁を生成する。外部I/O・待機（スリープ）を行わない。
- 利用するゲートウェイ実装は設定（環境変数で切替可能な設定値）で選択し、既定は模擬実装とする。services は境界の関数だけを呼び、実装クラスを直接 import しない。
- 呼び出しは、対象の注文行をロックしたトランザクションの内側で行う（ADDR-013 DD-003）。呼び出し前に注文の存在・所有を判定し、ロック取得後に読み直した状態が注文受付であることを確認する。確認できない場合は IF-01 を起動しない（ADDR-013 DD-002）。
- 応答待ちの締切を10秒とする。境界は呼び出し開始時刻を記録し、所要時間が10秒を超えた場合、呼び出しが例外で失敗した場合、および応答が IF-01-EXC-04 の条件（結果が承認・否認以外、結果または処理日時の欠落、承認で取引参照番号が欠落または形式不正、否認で否認理由コードが欠落）に該当する場合を、いずれも連携エラーとして扱う。模擬実装は待機を行わないため通常は締切に達しない。
- 連携エラー・否認の場合は決済記録（結果 error または declined）だけを登録し、注文状態・支払日時・在庫を変更しない。登録は呼び出しと同一のトランザクションで行い、コミット後に PAYMENT_SERVICE_ERROR（502）または PAYMENT_DECLINED（409）を返す（ADDR-013 DD-004）。
- 承認の場合は、呼び出し前に取得した注文行ロックを保持したまま、決済記録（承認）・注文状態の支払済への変更・支払日時・注文状態履歴を同一のトランザクションで確定する。状態の判定は呼び出し前の1回だけとし、承認応答を受けた決済要求が決済記録として残らない経路を作らない（ADDR-013 DD-001, DD-003）。
- 自動再送を行わない。再実行は購入者の操作による。
- 決済ゲートウェイへの要求・応答のログは、注文番号・決済金額・結果・取引参照番号・所要時間のみとし、個人情報・認証情報を含めない（ADDR-005）。
- カード番号等の決済手段情報を入力・保存・送信しない（NFR-LG-05）。

### 4.4 決定理由

NFR-PF-17 は「決済要求の送信・応答の受信を行う部分を他の処理から分離する」ことを求めており、独立モジュール＋データ構造限定の境界（OPT-001）がこれを構造として満たす。別プロセス化（OPT-002）は通信経路を再現できるが、構成制約（app・db の2サービス、外部接続禁止）と自動テスト実行の容易さを損なう。プロセス内呼び出しでは通信タイムアウトが自然には発生しないため、境界側で所要時間の締切判定と応答項目の検証を明示的に行い、IF-01-EXC-02〜04 を検出可能にする（DC-002）。呼び出しと結果の反映を注文行のロック区間に含めることで、同時支払・同時キャンセルでも承認済み決済記録を最大1件に保ち、注文受付以外の状態では決済要求を送信しない（DC-005、FR-031 6.16.9、ADDR-013）。
