## 3. 背景

### 3.1 判断が必要な理由

要件は出力形式（JSON Lines）・必須8項目・禁止項目・request_id の相関だけを定め、出力経路（ロガー構成・出力先）と相関付けの手段を定めていない。標準ライブラリ・外部ライブラリ・Webサーバーのアクセスログのいずれを用いるかで、必須項目の網羅と禁止項目の非出力の保証方法が変わるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- 全行が JSON として解析でき、リクエストごとの行に timestamp・level・request_id・method・path（クエリ文字列を含めない）・status・user_id（ログイン時）・duration_ms を必ず含める（NFR-OM-01）。
- パスワード・認証トークン・メールアドレス・氏名・住所・電話番号を全ログへ出力しない。マスキングではなく出力しない（NFR-SC-06、Steering 7.2）。
- X-Request-ID を受け取った場合は引き継ぎ、無い場合は生成し、応答ヘッダーへ付与する（NFR-OM-18）。
- 外部インターネットへ接続しない（NFR-EN-05）。依存ライブラリの追加は脆弱性確認・ライセンス確認の対象を増やす（NFR-SC-11、NFR-EN-12）。

### 4.3 決定内容

- ログは Python 標準 logging を用い、Django の LOGGING 設定（config/settings）で次を定義する。自作フォーマッタ（1イベント1行の JSON を ensure_ascii を偽にして出力）、自作フィルタ（contextvars から request_id・user_id をレコードへ注入）、ハンドラ（標準出力のストリームハンドラ）。ログ水準は環境変数で与える。
- ログ出力先は標準出力（コンテナのログ）に固定し、アプリケーションからファイルへ直接書かない。保管・ローテーションは運用側の設定とする（NFR-OM-02）。
- 共通ミドルウェア（shop/common に配置、ミドルウェア列の最外側）で次を行う。要求ヘッダー X-Request-ID があり 1〜64文字の英数字・ハイフンであればその値を採用し、無い・形式不正なら UUID4 の32桁16進文字列を生成する。contextvars に保持し、応答ヘッダー X-Request-ID へ付与する。処理時間を計測し、応答直前にリクエスト行を1件出力する。
- リクエスト行の項目は timestamp（ISO 8601、+09:00 付き）、level、request_id、method、path（request.path。クエリ文字列を含めない）、status、user_id（認証済みのときのみ。未ログインの行では項目自体を出力しない）、duration_ms（整数ミリ秒）とする。
- 業務ログ・例外ログは、あらかじめ定めた許可項目（request_id、処理名、注文番号、在庫単位ID、エラーコード、例外クラス名、処理時間）のみを渡す。任意の辞書・オブジェクトをそのまま出力しない。
- 禁止項目（パスワード、認証トークン、セッション識別子、メールアドレス、氏名、住所、電話番号）はログ呼び出しへ渡さない。要求本文・Authorization ヘッダー・クエリ文字列をログへ渡さない。
- 未処理例外は ADDR-007 の共通エラー処理で捕捉し、ERROR 水準で1行出力する（例外クラス名とスタックトレースはログにのみ出力し、応答には含めない）。例外メッセージに利用者入力値を埋め込まない。
- 監査ログ（D-15）はアプリケーションログと別経路で DB へ記録し、同じ禁止項目の制約を適用する。
- 初期データ一括投入（FR-060）の標準出力・標準エラー出力にも禁止項目を出力しない。

### 4.4 決定理由

必須項目の網羅（DC-001）と禁止項目の非出力（DC-002）は、出力地点を共通化しないと保証できない。共通ミドルウェア＋フォーマッタ（OPT-001）は、リクエスト行を1か所で生成するため項目の漏れが起こらず、許可項目方式により禁止項目の混入経路を閉じられる。request_id は contextvars に置くことで、ミドルウェア以降の services・models から呼ばれるログにも自動的に付与できる（DC-003）。外部ライブラリ（OPT-002）を入れても禁止項目の制御は自作のままであり、依存追加の正当性が無い（DC-004）。
