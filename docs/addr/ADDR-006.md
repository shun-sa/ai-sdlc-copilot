## 3. 背景

### 3.1 判断が必要な理由

要件は一覧の検索条件・並び順・件数上限と目標応答時間（参照系1.0秒、3年後データ量）だけを定め、索引と問い合わせの組み立て方を定めていない。索引設計と問い合わせ方式の選択によって、NFR-PF-01・NFR-PF-06 の達成可否と NFR-SC-04（プレースホルダ使用・文字列連結禁止）の遵守の担保方法が変わるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- DB の操作はプレースホルダで行い、SQL 文を入力値の文字列連結で組み立てない（NFR-SC-04）。
- 1回の応答件数は商品一覧・注文履歴・注文一覧が20件、在庫単位一覧が50件（NFR-PF-08）。
- 外部インターネットへ接続せず、app・db 以外のサービス（検索エンジン等）を追加できない（NFR-EN-05、NFR-EN-03）。
- 商品分類の階層は最大3階層（FR-060 の深さ制約）。
- 管理者の注文検索は購入者のメールアドレスを部分一致で受け取る（FR-041）。

### 4.3 決定内容

- 一覧検索の問い合わせは services 層で Django ORM の QuerySet として組み立て、生SQL・文字列連結・extra を使わない。検索条件値は常に QuerySet の引数として渡す。
- 次の索引をマイグレーション（TASK-002）で作成する。商品（D-04）：is_public と created_at の降順・id の降順を含む複合索引、name の索引。商品分類所属（D-05）：collection_id と item_id の複合索引。在庫単位（D-06）：item_id の索引、sku の一意索引、supplier_id の索引、price の索引。注文（D-10）：ordered_at の降順と id の降順を含む複合索引、order_number の一意索引、status の索引、buyer_id と ordered_at の降順の複合索引。利用者（D-01）：email の一意索引（正規化後の小文字で保存する）。
- FR-011 は、公開中かつ在庫単位を1件以上持つ商品の判定を在庫単位の存在判定（EXISTS 相当の Exists 注釈）で行い、最低税抜価格は在庫単位の最小価格の注釈（Subquery または集計）で求める。分類指定は、対象分類とその配下分類の分類IDを最大3階層分の親子関係から取得して IN 条件で渡す（再帰クエリを使わない）。キーワードは商品名・商品説明の大文字小文字非区別の部分一致（icontains）で OR 結合する。
- FR-032 は購入者ID＋注文日時降順の複合索引を用い、FR-041 は注文日時降順の複合索引を主に用いる。注文番号指定時は一意索引による完全一致を先に適用する。注文日の範囲は JST の日付境界を日時へ変換した範囲比較とし、列へ関数を適用しない。購入者メールアドレスは利用者との結合に対する部分一致とする。
- FR-040 は在庫単位から商品・仕入先を結合して取得し、1ページ50件とする。
- 総件数は同一条件の件数問い合わせで求め、ページ取得は LIMIT・OFFSET（QuerySet のスライス）で行う。1ページ件数は各FRの固定値とし、クライアントからの件数指定を受け付けない。
- 一覧で参照する関連データ（商品分類・在庫単位・購入者・注文明細）は select_related・prefetch_related で取得し、明細ごとの追加問い合わせ（N+1）を発生させない。
- 管理者の注文検索でメールアドレスをクエリで受け取るため、ログの path にクエリ文字列を含めない（ADDR-005 DD-005）。

### 4.4 決定理由

NFR-SC-04 は外部入力がクエリへ到達する経路（FR-011 のキーワード、FR-041 のメールアドレス）を持つため、組み立て方式そのものに安全性の根拠が必要である。ORM（OPT-001）は常にパラメータ化クエリを生成し、レビューでも「生SQLが無いこと」を機械的に確認できる（DC-002）。性能面では、対象件数が最大でも注文11万件であり、絞り込み・並び替えに一致する複合B-tree索引を置けば参照系1.0秒の目標を満たせる（DC-001）。部分一致のための拡張導入（OPT-003）や検索基盤追加（OPT-004）は、データ量に対して過剰であり構成制約にも反する。
