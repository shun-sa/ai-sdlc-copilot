## 3. 背景

### 3.1 判断が必要な理由

データ要件は識別子を「1以上の整数、システムが付与」とするが、内部の採番方式は設計に委ねている（data_requirements.md 1.2）。並び順（同一秒の登録順・追加順・記録順：LDR-014、LDR-015）の判定方法、削除指定（UPD-33）で全利用者を削除した後に投入した利用者へ削除前と同じ値を再付与してよいかには明示の定めがない（OQ-LDB-002）。監査ログは削除された利用者の識別子を保持し（DQ-48、NFR-SC-23）、削除前のログイン状態は削除後の利用者として認証されてはならない（FR-060 6.26.9）ため判断が必要。

### 3.2 判断時の制約

D-01-01 等の「1以上の整数」。PostgreSQL 16・Django ORM（NFR-EN-02、NFR-EN-09）。監査ログ・注文状態履歴は追記のみ（NFR-SC-23）。

### 4.2 検討した選択肢

| 選択肢ID | 選択肢 | 利点 | 欠点・リスク | 選定結果 | 根拠 |
|---|---|---|---|---|---|
| OPT-001 | テーブルごとのデータベース自動採番（64ビット整数の identity。Django の BigAutoField）とし、採番を初期化しない（削除指定の後も値を再利用しない）。並び順の同値は識別子の昇順で判定 | 一意・不変・増加をデータベースが保証し、再利用しないため監査ログの値が新しい利用者を指さない。挿入順に増加するため登録順・記録順を再現できる | 識別子に欠番が生じる | SELECTED | DC-001〜DC-004 |
| OPT-002 | 自動採番とし、削除指定のときに採番を初期化する（TRUNCATE と採番の巻き戻し） | 検証環境の初期化後に識別子が小さい値から始まる | 削除前の利用者の識別子と同じ値が新しい利用者に付与され、監査ログの解釈とログイン状態の切り分けが曖昧になる | NOT_SELECTED | DC-002 |
| OPT-003 | UUID 等の非整数の識別子 | 推測されにくい | D-01-01 等の「1以上の整数」に反し、登録順を識別子で判定できない | NOT_SELECTED | DC-001、DC-003 |
| OPT-004 | アプリケーションで最大値＋1 を採番 | 追加の仕組みが不要 | 同時登録で重複し、防ぐには表全体のロックが必要 | NOT_SELECTED | DC-004 |

### 4.3 決定内容

OPT-001 を採用する。LDB-001 でシステム付与識別子を持つ Entity（ENT-001〜ENT-004、ENT-006、ENT-008〜ENT-010、ENT-013〜ENT-015 ほか、ENT-005・ENT-011・ENT-012・ENT-007 の物理上の代替キーを含む）は、テーブルごとの64ビット整数の自動採番（1から開始、1ずつ増加）を主キーとする。採番はいかなる場合も初期化・巻き戻しをせず、削除指定付きの初期データ一括投入でもデータは DELETE で削除し採番は継続する（ADDR-004 DD-008）。同じ日時の並び順（商品の登録順、カート明細の追加順、決済記録・注文状態履歴の記録順）は識別子の昇順で判定し、初期データ一括投入は定義ファイルの記載順に1行ずつの順序を保って登録する。注文明細は確定時のカートの並び（追加順）で登録し、注文明細の識別子の昇順で並びを再現する。監査ログの対象の利用者は利用者の識別子の値を保持し、利用者の削除後も値を残すため参照整合性制約（外部キー）を定義しない。Web API では識別子を JSON の整数で返し、パス・入力で整数として解釈できない値は対象なしとする（ADDR-001 DD-007）。

### 4.4 決定理由

OPT-001 は一意・不変・正の整数をデータベースが保証し（DC-001）、実行単位を増やしても重複しない（DC-004）。採番を初期化しないため、削除指定の前後で同じ識別子が別の利用者に付くことがなく、監査ログの対象の利用者の値が削除後の利用者を指すことも、削除前のログイン状態が削除後の利用者として認証されることも構造的に起きない（DC-002）。挿入順に値が増えるため同一秒の順序を識別子で再現できる（DC-003）。OPT-002 は DC-002 を満たさず、OPT-003 は整数の要件に反し、OPT-004 は同時登録に弱い。
