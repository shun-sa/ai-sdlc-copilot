## 3. 背景

### 3.1 判断が必要な理由

要件は「無操作30分で切断」「HttpOnly、本番はSecure」「ログイン成功時に識別子を再発行」「Cookie認証の全更新要求でCSRFトークンを検証」までを定めるが、セッションの保存先（Cookie本体・DB・キャッシュ）、無操作時間の計測方法、CSRFトークンの実装手段を定めていない。保存先はNFR-PF-16（状態をDBへ保持）に直結し、実装前に確定する必要がある。

### 3.2 判断時の制約

- 利用者の状態（ログインセッション）をアプリの内部メモリではなくDBへ保持する（NFR-PF-16）。
- Docker Compose のサービスは app と db の2つで、キャッシュ基盤等を追加しない。
- 外部CDN・外部サービスへ接続しない。追加の依存ライブラリを導入しない。
- 画面と API は同じ業務ロジックを呼ぶ（画面がAPIをHTTPで呼び出す構成にしない）。
- 検証環境はHTTPを許容するため、Secure属性を環境によって切り替えられる必要がある。

### 4.3 決定内容

- セッション：`django.contrib.sessions` を有効にし、`SESSION_ENGINE` を DB バックエンド（`django.contrib.sessions.backends.db`）とする。セッションにはログイン利用者の識別子とロールのみを保持し、個人情報・パスワード・APIトークンを保持しない。
- Cookie属性：`SESSION_COOKIE_HTTPONLY = True`、`SESSION_COOKIE_SAMESITE = "Lax"` を固定とし、`SESSION_COOKIE_SECURE` は環境変数で切り替える。環境変数が未設定・空・解釈できない値の場合の既定値は真（Secure を付与する）とし、検証環境（ENV-01）でHTTPを使う場合にだけ環境変数へ明示的に偽を設定する。設定値の解釈は `common` の単一の真偽値読み取り処理で行い、未設定時に偽へ倒れる実装（フェイルオープン）にしない。
- 無操作切断：`SESSION_COOKIE_AGE = 1800`（30分）と `SESSION_SAVE_EVERY_REQUEST = True` を設定し、画面からの要求を受け付けるたびに有効期限を延長する。期限切れ後の操作はログイン画面へ遷移させ、切断された旨を表示する。
- 識別子の再発行：ログイン成功時に `cycle_key()` 相当でセッション識別子を再発行し、ログアウト時はセッションを破棄（`flush()` 相当）する。
- ログイン後の復帰：未ログインで要求された画面のパスをセッションへ保持し、ログイン成功後にそのパスへ戻す。戻り先は自サイト内の相対パスだけを許可し、外部URLへは遷移しない。
- CSRF：`CsrfViewMiddleware` を有効にし、画面の全フォームにCSRFトークンを埋め込む。`CSRF_COOKIE_SAMESITE = "Lax"`、`CSRF_COOKIE_SECURE` は `SESSION_COOKIE_SECURE` と同じ規則で環境変数から読み取り、未設定・空・解釈できない値の場合の既定値は真とする。画面からの更新操作はPOSTのみとし、GETで状態を変更しない。
- APIとの分離：APIはBearerトークンで認証し、Cookieセッションによる認証（DRFのSessionAuthentication）を使わない。したがってAPIはCSRFトークン検証の対象外とする。

### 4.4 決定理由

DC-001〜DC-004 をすべて満たし、かつ追加のサービス・依存を増やさないのはDjango標準のDBセッションと標準CSRF機構である。Cookie格納方式（OPT-002）は状態のDB保持と即時無効化の要件に反する。独自実装（OPT-003）は標準同等機能の再実装であり、脆弱性対策基準に対して不利になる。ログイン後の戻り先をクエリ文字列ではなくセッションで持つのは、外部URLへの誘導（オープンリダイレクト）を構造的に防ぐためである。
