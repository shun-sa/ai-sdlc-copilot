## 3. 背景

### 3.1 判断が必要な理由

Steering は画面・API・業務処理を単一 Django プロジェクトに置き、業務規則を画面側に重複実装しないことを指定するが、内部のモジュール分割・依存方向は指定していない（Steering 4章・5章）。画面と API の同一判定（CMN-34、NFR-LG-06、VUL-07）、処理能力の増強（NFR-PF-16）、決済連携の差替え（NFR-PF-17）は構成に依存するため判断が必要。

### 3.2 判断時の制約

Django 5.2 のテンプレートによるサーバーサイドレンダリング、DRF、JavaScript は最小限、SPA・フロントエンドのビルドは使わない（Steering 3章、NFR-EN-09）。全 API・全画面で権限を判定（NFR-SC-03）。

### 4.3 決定内容

OPT-001 を採用する。

1. 分割：app/ 配下を、common（時刻提供点・入力正規化・業務例外とエラー種別・ページング・ログ・送信トークン）、accounts（会員・認証）、catalog（商品分類・商品・在庫単位・仕入先）、promotions（クーポン）、carts（カート・金額計算 FR-026）、orders（注文確定・支払・キャンセル・出荷・配達完了）、payments（決済ゲートウェイの境界と模擬実装）、audit（監査ログ）、initial_data（初期データ一括投入の管理コマンド）、test_support（試験支援。開発用機能フラグ有効時のみ：ADDR-011）の Django アプリに分ける。
2. 層と依存：各アプリは業務処理層（services）・モデル・画面ビュー（テンプレート）・API ビュー（DRF）を持つ。依存はビュー→業務処理層→モデル・決済ゲートウェイの境界の一方向とし、業務処理層は Django の HTTP 要求・DRF・テンプレートに依存しない。業務処理層は業務例外（ERR-01〜ERR-08 の種別と業務エラーの種類・判定値）を送出し、画面と API はそれぞれ共通の変換部品で通知に変える。
3. 入力：画面のフォームと API のシリアライザは値の取出しと型の変換だけを行い、CMN-13〜CMN-16 の入力判定・判定順序は業務処理層で行う。
4. 権限：ビューで認証・利用者区分を判定し、業務処理層でも所有者で絞り込んだデータだけを扱う（他の購入者のデータは対象なし）。
5. 決済：orders の支払処理は payments の境界（ADDR-008）だけに依存し、模擬実装を直接参照しない。
6. 状態：実行単位のメモリ・ローカルファイルに業務状態・ログイン状態・カートを保持しない（全てデータベース）。
7. 出力：テンプレートの自動エスケープを常に有効とし、利用者・データ由来の値に safe・mark_safe 等のエスケープ解除を使わない。
8. データアクセス：ORM（パラメータ化）だけで SQL を発行し、SQL の文字列連結・利用者入力を含む生 SQL を使わない（アドバイザリロック等の生 SQL は定数とパラメータだけ）。OS コマンド・シェルを業務処理から起動しない。
9. 追記のみの記録：監査ログ・注文状態履歴・決済記録のモデルは更新・削除の操作を業務処理に公開しない（削除は一括投入の削除指定（監査ログを除く）と運用者の保存期間経過分の削除に限る）。
10. フレームワーク付属の特権経路（r2 追加。SR-ADDR-001）：
    - django.contrib.admin を INSTALLED_APPS に含めず、admin/ 等の Django 管理サイトの URL を設けない。管理者向けの機能は FR-040〜FR-045 の画面と /api/admin/ だけとし、それ以外の管理用 URL・内部用エンドポイントを公開しない（django.contrib.auth・contenttypes・sessions は認証・セッションのためだけに使う）。
    - 利用者モデルは ENT-001 に対応する独自モデル（AbstractBaseUser を基にし PermissionsMixin を使わない）とし、is_staff・is_superuser・グループ・個別権限を持たせない。管理者の判定は利用者区分（user_type=admin。ADDR-007）だけで行う。
    - 管理者の作成・利用者区分の変更は初期データ一括投入（FR-060。ADDR-010 の管理コマンド）だけで行う。Django 付属の createsuperuser・changepassword は accounts アプリの同名の管理コマンドで置き換え（accounts を django.contrib.auth より前に INSTALLED_APPS へ置く）、何も変更せずにエラー終了させる。

### 4.4 決定理由

OPT-001 は判定を業務処理層の1か所に置き、画面と API の両方がそれを呼ぶため、判定順序・業務規則・エラー種別が構造上一致する（DC-001）。決済は境界越しにだけ呼ぶため実装の差替えが他の処理に波及しない（DC-002）。状態をデータベースに限ることで実行単位を自由に増やせる（DC-003）。画面は Django テンプレートで描画するため Steering の SSR・最小 JavaScript の制約に合う（DC-004）。Django 付属の管理サイトと特権フラグは、既定のままでは FR-060 以外の管理者作成・権限付与の経路と外部から到達できる管理画面を生むため、構成から除き、管理者の判定を利用者区分だけに一本化する（DC-005。r2 追加）。OPT-002 は Steering に反し、OPT-003 は判定が分散する。
