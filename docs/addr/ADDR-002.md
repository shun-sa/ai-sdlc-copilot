## 3. 背景

### 3.1 判断が必要な理由

要件は Web API のログイン状態の24時間有効・ログアウトでの無効化・128ビット以上相当の推測困難性（NFR-SC-08）、画面の無操作30分（NFR-SC-09）、多重ログインと個別ログアウト（NFR-SC-18、CMN-11・CMN-12）、セッション固定化・乗っ取り防止とスクリプトからの参照不可（NFR-SC-19）、CSRF 対策（NFR-SC-05）、削除指定で削除した利用者のログイン状態の無効化（FR-060 手順9）を定めるが、保持・失効・CSRF 対策の方式は定めていない。ログイン状態はデータ要件の対象外で、論理モデルへの追加の要否も判断が必要（OQ-LDB-005）。

### 3.2 判断時の制約

Steering 6.2（API は Bearer、画面はセッション）。Django 5.2・DRF（NFR-EN-09）。処理能力の増強（実行単位の追加）でログイン状態を失わない（NFR-PF-16）。有効期限の境界を試験用の現在時刻で再現できる（NFR-OM-06 (1)、AC-UC-002-011）。ログイン状態を示す情報をログに出力しない（NFR-SC-06）。

### 4.3 決定内容

OPT-001 を採用する。

1. Web API のログイン状態：ログイン成功時に OS の暗号論的乱数で256ビットの値を生成し、URL 安全な文字列として利用者へ返す（ADDR-001 の token）。データベースにはその SHA-256 照合値、利用者（ENT-001 の識別子）、ログイン時刻、有効期限日時（ログイン時刻（秒単位に切り捨て）＋24時間）だけを保持し、値そのものは保持しない。1回のログインにつき1行とし、既存の行は変更しない（多重ログイン）。
2. API の認証判定：Authorization の Bearer 値の照合値で行を検索し、行があり、かつ判定時刻（秒単位に切り捨て）＜有効期限日時の場合だけ有効とする。ログアウトはその要求の行だけを削除する。期限切れの行は判定で無効とし、削除は任意の契機でよい。
3. 画面のログイン状態：Django セッション（データベース保持）を用い、ログイン成功時にセッション識別子を再生成する（固定化防止）。セッションに最後に画面要求を受け付けた時刻を保持し、要求ごとに「判定時刻（秒）−最後の受付時刻 ≧ 30分」なら当該セッションを破棄して SCR-004 へ遷移させ、切断された旨を表示する。それ以外は最後の受付時刻を更新する。セッション Cookie は HttpOnly・SameSite=Lax とし、本番では Secure（ADDR-014）。
4. 判定時刻：有効期限・無操作の判定はすべて共通の時刻提供点（ADDR-011）から取得した時刻で行う。
5. CSRF 対策：画面のすべての更新操作を POST とし、Django の CSRF 対策（フォームの CSRF トークンと Cookie の照合）を全画面に適用する。CSRF Cookie は HttpOnly・SameSite=Lax、本番では Secure。/api/ は Bearer 認証のみで Cookie を認証に使わないため CSRF 対策の対象外とする（ADDR-001 INV-003）。FR-020（カート照会）の画面表示（SCR-005・SCR-006、共通表示の合計点数）に伴う利用中カートの作成は利用者の更新操作に当たらず GET の表示で行う。その範囲・冪等性・一意性は ADDR-001 4.3 の14・DD-015・DD-016（r3）を正とする（r2 追記）。
6. 削除指定時の無効化：FR-060 の削除指定では、同じトランザクションの中で、全 API ログイン状態の行と全画面セッションを削除する。あわせて利用者の識別子を再利用しない（ADDR-006）ため、削除前のログイン状態が削除後に投入された利用者として認証されることはない。
7. 論理モデル：ログイン状態はデータ要件の対象外（data_requirements.md 1.2）の技術的な保持データとし、業務 Entity として LDB-001 に追加しない。物理テーブルは実装（マイグレーション）で ENT-001 に従属して定義する。

### 4.4 決定理由

OPT-001 だけが、個別ログアウト・多重ログイン・削除指定時の一括無効化を行の削除で即時に実現でき（DC-001）、保持先がデータベースのため実行単位を追加しても状態を共有できる（DC-003）。照合値だけを保持するのでデータベースが漏えいしても値を再利用されにくい。有効期限と無操作を独自の判定で行うことで、試験用の現在時刻で境界を再現できる（DC-002）。乱数256ビットは NFR-SC-08 の128ビット以上を満たし、Django 標準のセッション再生成・HttpOnly Cookie・CSRF 対策で NFR-SC-05・NFR-SC-19 を満たす（DC-004）。JWT は失効に結局データベースを要し、authtoken は多重ログインを満たせず、API の Cookie セッションは Steering に反する。
