## 3. 背景

### 3.1 判断が必要な理由

要件は認証状態の性質（128ビット以上相当の乱数、有効期間24時間、ログアウトで無効化、多重ログイン可、画面は無操作30分、ログイン時のセッション識別子再発行）だけを定め、保持先と検証経路を定めていない。自己完結型トークン（JWT）と参照型トークン（DB保持）では、ログアウト時の即時無効化の実現性が大きく異なるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- 利用者の状態（画面のログインセッション・API の認証トークン・カート）を app の内部メモリではなく DB に保持すること（NFR-PF-16）。
- 技術スタックは Python 3.12・Django 5.2 LTS・DRF 3.15 以上・PostgreSQL 16 に固定され、キャッシュ用の追加サービスを置けない（Steering 3章、NFR-EN-03）。
- ログアウト後・有効期限到達後のトークンでの要求は受け付け0件であること（NFR-SC-08）。
- 同一利用者の多重ログインを許可し、一方のログアウトで他方を無効化しないこと（NFR-SC-18）。
- 認証系APIの応答時間は95パーセンタイルで2.0秒以内（NFR-PF-09）。
- FR-060 手順9（全削除指定）は監査ログ以外の全データを削除し、削除した利用者の認証トークン・ログインセッションが無効になることを求める。削除と投入は同一トランザクションで確定する（FR-060 手順12、CMN-21）。

### 4.3 決定内容

- 認証トークンデータ（新規の永続データ。項目：利用者、トークンハッシュ、発行日時、有効期限日時、無効化日時）を DB に持つ。FR-002 のログインごとに1件を新規登録し、既存の有効なトークンは無効化しない（NFR-SC-18）。
- トークン値は暗号論的に安全な乱数（secrets モジュール）で 256ビット（32バイト）を生成し、URL安全な文字列として応答する。DB には SHA-256 ハッシュ（16進文字列）を一意制約付きで保存し、平文のトークン値を保存しない。照会はハッシュ一致で行う。
- 有効期限日時＝発行時刻＋24時間。検証は「無効化日時が未設定」かつ「判定時刻＜有効期限日時」で行い、有効期限日時ちょうどは無効とする。
- FR-003（ログアウト）は、要求に使われたトークンの無効化日時を設定する。無効化済み・期限切れ・不一致のトークンは AUTHENTICATION_REQUIRED（401）とする。
- API の認証は DRF の認証クラス1つに集約し、Authorization ヘッダーの Bearer 形式を解釈する。認証不要API（FR-001, FR-002, FR-010, FR-011, FR-012）には適用しない。
- 画面は Django の認証セッションを使い、設定を次のとおり固定する。セッションバックエンドは DB（django.contrib.sessions.backends.db）、SESSION_COOKIE_HTTPONLY は真、SESSION_COOKIE_SECURE は環境変数で与え本番環境は真、SESSION_COOKIE_AGE は1800秒、SESSION_SAVE_EVERY_REQUEST は真（最後の操作からの無操作30分とするため）。
- 画面のログイン成功時は Django の login 処理によりセッション識別子を再発行し、ログイン前の識別子を無効化する（NFR-SC-19）。ログアウト時はセッションを破棄する。
- 画面からの更新要求には CSRF 対策用トークンの検証を適用する（NFR-SC-05）。API のトークン認証経路には Cookie を用いないため CSRF 対策用トークンを要求しない。
- 画面とAPIのどちらで認証しても、後続の業務ロジックには同一の利用者・ロールを渡す（ADDR-004 の services 層を共用する）。
- 期限切れ・無効化済みのトークン行は削除せず保持する（削除要件が無いため）。トークン値・ハッシュをログへ出力しない。
- 全削除指定（FR-060 手順9）での扱いを次のとおり確定する。要件上、利用者を削除する操作は FR-060 手順9 だけであり、これ以外に利用者削除の機能を追加しない。
  - 認証トークンデータの利用者参照は親（利用者）の削除に連動して削除する（Django の on_delete=CASCADE、DB 側も ON DELETE CASCADE）。これにより、全削除で利用者行を削除しても認証トークンが参照整合性違反で残らず、AC-UC-013-004 の全削除実行が失敗しない。
  - 全削除指定の実行時は、利用者等の削除と同一トランザクション（FR-060 手順12）内で、Django のセッション表の全行を削除する。全利用者が削除されるため、認証状態を持つログインセッションはすべて無効化対象となる。認証状態を持たない匿名セッションも同じ表に混在するが、次回アクセス時に再作成されるため要件上の機能喪失はない。
  - 削除対象は認証トークンデータとセッション表に限り、監査ログ（D-15）は削除しない。認証トークンデータとセッション表は AC-UC-013-004 が件数を照合する業務データ（利用者・仕入先・商品分類・商品・商品分類所属・在庫単位・クーポン・カート・注文系）に含まれないため、件数照合の対象外とする。
  - 全削除指定が無い投入では、認証トークン・ログインセッションを削除・無効化しない（FR-060 手順9 は実行されない）。
- 実装先Taskの配置を次のとおり統一する。本ADDRが導入する永続オブジェクト（認証トークンデータのモデルと一意制約・索引を含むマイグレーション）は TASK-002（MIGRATION）で作成する。ADDR-003 の注文番号シーケンス、ADDR-006 の索引と同じ配置規則であり、D-01〜D-15 以外の要件由来の永続オブジェクトも TASK-002 にそろえる。TASK-005 はトークンの生成・照会・無効化と DRF 認証クラス、TASK-014 は全削除時の無効化、TASK-001・TASK-015 は設定を担当する。
  - 認証トークンデータは NFR-PF-16（利用者の状態を app の内部メモリではなく DB に保持する）と NFR-SC-08・NFR-SC-18 に基づく要件由来の永続データであり、TASK-002 の完了条件「要件に無いデータ項目・テーブルを追加していない」に反しない。同完了条件の「D-01〜D-15 に対応するモデルが定義されている」は、要件由来の追加オブジェクトの作成を妨げない。
  - この配置により、TASK-002 が TASK-005 と TASK-014 の双方を先行（Blocks）するため、TASK-014（Wave 3、依存は TASK-002・TASK-004）が全削除で認証トークンデータを操作する時点で表が存在する。
  - 画面のログインセッションは Django 標準の django.contrib.sessions が持つセッション表を使い、独自モデル・独自マイグレーションを作らない。同アプリの有効化（INSTALLED_APPS、SESSION_ENGINE＝DB バックエンド）は TASK-001 の Django プロジェクト設定で行い、TASK-002 の migrate でセッション表が作成される。Cookie 属性・有効期間の設定値は TASK-015 で固定する。

### 4.4 決定理由

DC-001 と DC-002 を同時に満たすには、サーバー側で個々の認証状態を識別・無効化できる必要がある。参照型トークン（OPT-001）は、無効化日時の設定だけで以後の要求を確実に拒否でき、ログインごとの新規登録で多重ログインも自然に表現できる。JWT（OPT-002）は失効リストのために結局 DB 保持が必要となり、利点が残らない。画面側は Django の DB セッションが無操作タイムアウト・識別子再発行・Cookie 属性を標準設定で満たすため、独自実装より検証（NFR-SC-09・NFR-SC-19 のセキュリティテスト）が容易である。1要求あたりの追加DBアクセスは索引による1件照会であり、NFR-PF-09 の2.0秒に対して影響は小さい。

DC-006 について、参照型トークン（OPT-001）は認証状態が利用者行に紐づく独立した行であるため、FR-060 手順9 の全削除では親の削除に連動させるだけで無効化が成立する。無効化を明示しない場合、実装は「認証トークンを残して参照整合性で失敗する（AC-UC-013-004 が不成立）」と「削除済み利用者の認証状態が残存する（NFR-SC-08 の趣旨に反する）」のどちらにも転び得るため、本ADDRで扱いを一意に固定する。実装先Taskの配置は、ADDR-003・ADDR-006 と同じく永続オブジェクトを TASK-002 に集約する規則をとる。TASK-005 側に置くと、TASK-005 と同じ Wave で並行する TASK-014 が未作成の表を前提にすることになり、依存順（TASK-002 が TASK-005・TASK-014 を Blocks）と一致しない。
