## 3. 背景

### 3.1 判断が必要な理由

要件と提供済みAPI契約はエラーコード・HTTPステータス・応答内容（システムエラーはエラーコードと利用者向け文言のみ）を定めるが、どの機構で例外を捕捉し、どの範囲をどのコードへ写像するかを定めていない。TASK-003 の Notes も実現方式を独立ADDR工程へ委ねている。方式が未確定だと、機能Taskごとに個別の try/except でエラー応答を組み立て、内部情報の混入や判定順序のずれが生じる。

### 3.2 判断時の制約

- エラーコード・HTTPステータス・context の内容を変更・追加しない。
- 応答にスタックトレース・SQL文・ファイルパス・ライブラリ名とバージョンを含めない。
- 判定順序（認証→権限→入力→対象の存在・所有→状態→業務ルール）を変えない。
- ログイン（FR-002）の資格情報照合失敗は `INVALID_CREDENTIALS`（401）で返し、メールアドレスとパスワードのどちらが誤りかを区別しない。未入力のみ `VALIDATION_ERROR`（提供済みAPI契約 6.2）。
- 同時実行の競合に専用のエラーコードを設けず、既存の業務エラーで返す（CMN-19）。同一メールアドレスの同時登録の後着は `EMAIL_ALREADY_REGISTERED`（409）となる（E-001-02）。
- 入力エラーは不備のある全項目を列挙する。
- 画面とAPIは同一の業務ロジック・判定順序・エラーコードに従う。
- 追加の依存ライブラリを導入しない。

### 4.3 決定内容

- `common` に業務例外の基底クラスを定義する。保持する属性はエラーコード、利用者向け文言、`details`（項目別の理由、既定は空配列）、`context`（既定は空オブジェクト）とし、業務エラーごとの派生クラス（在庫不足・数量上限超過・クーポン各種・状態遷移不正・カート空・メールアドレス重複・決済否認・外部連携エラー等）を用意する。認証失敗（資格情報の照合失敗）は業務例外ではなく専用の認証失敗例外として定義し、認証情報の不在・無効を表す認証例外とは別の型にする。
- DRFの `EXCEPTION_HANDLER` を独自関数へ差し替え、次の分岐順で例外の種別を判定して写像する。これは送出された例外を種別ごとに振り分ける順序であり、各機能内の判定順序（①認証→②権限→③入力形式→④対象の存在・所有→⑤状態→⑥業務ルール、CMN-14）は処理側が守る。本ADDRは判定順序とAPI契約のエラーコード・HTTPステータスを変更しない。
  1. 認証に関する例外
     - 1-a. 認証情報が提示されていない・無効・期限切れ（未ログイン、ログアウト済み、トークン期限切れ） → `AUTHENTICATION_REQUIRED`（401、ERR-04）
     - 1-b. 提示された資格情報の照合に失敗（FR-002 のログイン。メールアドレス未登録・パスワード不一致・メールアドレスの形式不正を区別しない） → `INVALID_CREDENTIALS`（401、ERR-05）。ログイン処理は認証失敗例外を送出し、1-a の認証例外を流用しない。ログインの未入力は 3 の検証例外として `VALIDATION_ERROR` になる
  2. 権限に関する例外 → `PERMISSION_DENIED`（403）
  3. 検証例外 → `VALIDATION_ERROR`（400、不備のある全項目を `details` へ列挙）
  4. 対象なし例外 → `NOT_FOUND`（404）
  5. 業務例外（基底クラスの派生） → 例外が持つエラーコードとHTTPステータス（409・502）
  6. DB整合性例外（一意制約違反・検査制約違反等） → 違反した制約名を鍵に `common` の「制約名→業務例外」の対応表を引き、一致する場合は対応する業務例外へ変換して 5 と同じ写像を適用する。一致しない場合だけ 7 へ送る
  7. 上記以外の未捕捉例外 → `INTERNAL_ERROR`（500）
- DB整合性例外の変換責務は次のとおり分担する。業務として起こり得る整合性違反（会員登録時のメールアドレス重複、同一メールアドレスの同時登録の後着）は、第一責務としてサービス層が整合性例外を捕捉して対応する業務例外を送出する。分岐 6 は取りこぼしがあった場合でも `INTERNAL_ERROR` へ落とさないための最後の防御として働く。ADDR-003（同時実行制御）および ADDR-008（一意制約の物理設計）が本ADDRへ委ねている「一意制約違反→業務エラー」の写像は、この対応表が正本となる。
- 「制約名→業務例外」の対応表の初期内容は、利用者の正規化済みメールアドレスの一意制約 → `EMAIL_ALREADY_REGISTERED`（409、context は空オブジェクト）とする。制約名は ADDR-008 のマイグレーションで定義した名称を正本とし、対応表と制約定義で同じ名称を用いる。これ以外の一意制約違反・検査制約違反（在庫数量の下限など）は、先行する業務判定（ADDR-003 の行ロック後の再判定）によって業務上到達しないため対応表へ載せず、7 の `INTERNAL_ERROR` として扱う（最後の防御）。
- 未捕捉例外は応答生成の前に相関ID付きでログへ記録（例外種別・メッセージ・スタックトレースはログのみ）し、応答にはエラーコードと利用者向け文言だけを載せる。分岐 6 で業務エラーへ変換した整合性例外も、変換した旨と制約名を相関ID付きでログへ記録する（応答には含めない）。
- エラーコードとHTTPステータスの対応表は `common` の単一モジュールに定義し、ビュー・サービスで個別に定義しない。
- 画面は同じ業務例外を捕捉し、入力エラーは項目近傍、業務エラーはメッセージ領域へ表示する。未捕捉例外はエラー画面（SCR-901）へ遷移し、内部情報を表示しない。
- デバッグ表示は無効化した設定を既定とする。

### 4.4 決定理由

DC-001〜DC-003 を同時に満たすには、フレームワークの例外処理の入口を差し替え、業務例外を型として表現する方式が適している。個別 try/except（OPT-002）は機能数に比例して重複し一貫性を保てない。ミドルウェア方式（OPT-003）は検証エラーの項目別情報を失うため、全項目列挙の要件を満たせない。業務例外に context を持たせることで、提供済みAPI契約が定める業務エラーの context を発生源で組み立てられ、写像側で業務知識を持たずに済む。認証失敗を認証例外と別の型に分けるのは、どちらも401でありながらエラーコードが `AUTHENTICATION_REQUIRED`（ERR-04）と `INVALID_CREDENTIALS`（ERR-05）に分かれ、型が同じだと写像側で区別できず FR-002 のログイン失敗が ERR-04 として返るためである（DC-007）。DB整合性例外の分岐を業務例外と未捕捉例外の間に置くのは、ADDR-003・ADDR-008 が本ADDRへ委ねた一意制約違反の写像先を明示し、CMN-19・E-001-02 が求める `EMAIL_ALREADY_REGISTERED` が `INTERNAL_ERROR` に落ちないようにするためである。
