## 3. 背景

### 3.1 判断が必要な理由

NFR-EN-08 はミドルウェアの目標値を「指定なし（app サービス内で動作する Web サーバー・AP サーバーは設計で選定する）」とし、本番環境で Django 付属の開発用サーバーを使用しないことだけを制約として明示的に設計へ委譲している。選定しないと TASK-001 の起動設定と TASK-016 の起動手順が確定せず、NFR-EN-08 の検証（構成・設定レビュー）も成立しない。

### 3.2 判断時の制約

- 本番環境で Django 付属の開発用サーバーを使用しない（NFR-EN-08、VUL-08）。
- Docker Compose のサービスは app・db の2つ（Steering 3章・4章、NFR-EN-03）。追加サービスを置かない。
- 外部CDNを使わず、外部ネットワークへ接続しない（NFR-EN-05）。静的ファイルは自システムから配信する。
- 依存ライブラリはバージョンを固定し、公式の配布元から取得し、サポート期限内の版・利用可能なライセンスであること（VUL-10、NFR-EN-10、NFR-EN-12、NFR-SC-11）。
- 構成はコマンド1回で全サービスが起動すること（NFR-OM-05）。
- Django 5.2 LTS は同期（WSGI）構成で動作し、本リリースは非同期ビューを使わない（Steering 3章）。

### 4.3 決定内容

- app サービスの AP サーバーを Gunicorn とし、config の WSGI アプリケーションを 0.0.0.0 の 8000番で待ち受ける。compose.yaml の app サービスの起動コマンドを Gunicorn の起動とし、検証環境・本番環境で同一の起動方式を用いる。
- Gunicorn の設定値（ワーカー数、要求タイムアウト、待ち受けアドレスとポート、ログ水準）は環境変数で与え、既定値をコードへ埋め込まない。アプリケーションログは標準出力の JSON Lines（ADDR-005）とし、Gunicorn のアクセスログはアプリケーションログの代替としない。
- ワーカーは同期ワーカーとする（Django 5.2 の同期 WSGI 構成に合わせる）。非同期ワーカー・スレッド共有の状態を前提にしない。利用者の状態は DB に保持する（NFR-PF-16、ADDR-002）。
- 静的ファイルは Django の staticfiles で収集（collectstatic）し、WhiteNoise のミドルウェアで app プロセスから配信する。外部CDN・別サービスを使わない。
- 依存定義ファイルに Gunicorn と WhiteNoise をバージョン固定で追加し、取得元を公式の配布元に限る。いずれも NFR-SC-11 のリリース前脆弱性確認、NFR-EN-10 のサポート期限確認、NFR-EN-12 のライセンス確認の対象一覧に含める。
- 開発用サーバー（manage.py runserver）は compose.yaml・README の起動手順に記載しない。
- 本番環境ではデバッグ表示を無効化し、接続を受け付けるホスト名を環境変数で限定する（VUL-08、NFR-SC-10）。
- README（TASK-016）に Gunicorn による起動・ワーカー数の設定・静的ファイル収集の手順を記載する（NFR-OM-19）。

### 4.4 決定理由

NFR-EN-08 の制約は「開発用サーバーを使わない」ことだけであり、残る判断基準は構成制約（DC-002・DC-003）と運用・保守の容易さ（DC-004・DC-005）である。Gunicorn は Django の標準的な WSGI 実行方式で、設定が少なく構成・設定レビューが容易であり、プロセス数の増加で負荷増へ対応する NFR-PF-16 の方針とも一致する。静的ファイルは外部CDN禁止かつ追加サービス不可という制約下で app プロセスから配信するほかなく、WhiteNoise が Django 公式ドキュメントでも案内される同一プロセス配信の標準手段である。uWSGI・ASGI サーバー・リバースプロキシ追加は、本リリースの制約と規模に対して利点が制約を上回らない。
