## 3. 背景

### 3.1 判断が必要な理由

要件は「同時実行は逐次実行と同じ結果」「途中失敗はその操作の変更を残さない」「同一カートから注文1件」「承認の決済記録は最大1件」「画面で処理完了までの繰り返し操作は1回分だけ反映、支払の決済要求は1回分だけ送信」を求める（CMN-19〜CMN-23、NFR-PF-07、NFR-US-10）が、ロック・制約・分離レベル・トランザクション境界の方式は定めていない（OQ-LDB-011）。

### 3.2 判断時の制約

PostgreSQL 16 と Django ORM（NFR-EN-02、NFR-EN-09）。実行単位を追加しても成立すること（NFR-PF-16）。注文確定 240件/時以上、更新系 API 2.0秒以内（NFR-PF-04、NFR-PF-02）。競合専用のエラーを設けず、競合は在庫不足・状態不正・カートが空・メールアドレス登録済みの業務エラー、削除済み明細は対象なしで通知する（CMN-19）。システム障害時に自動再試行しない（E-030-11 等）。

### 4.3 決定内容

OPT-001 を採用する。

1. 分離レベルは PostgreSQL 既定の READ COMMITTED とする。更新を伴う業務処理（FR-001〜FR-003、FR-020〜FR-025、FR-030、FR-031、FR-034、FR-043〜FR-045、FR-060）は業務処理層（ADDR-012）の1関数を1トランザクション（transaction.atomic）で実行する。Django の ATOMIC_REQUESTS は使わず、業務処理層で境界を明示する。
2. ロック順序：⓪画面の要求に限り、業務処理のトランザクションの開始前に操作種別と送信トークンの組の単位のアドバイザリロック（11。r3 改訂、r4 改訂）、①親行（利用中カート、または注文）を SELECT FOR UPDATE、②関係する在庫単位を識別子の昇順で SELECT FOR UPDATE、③注文番号の採番ロック（注文確定のみ。ADDR-005）。この順序以外でロックを取らない。ロック取得後に、受付時点の最新データで各 FR の手順（判定順序を含む）を実行する。
3. 注文確定（FR-030）：購入者の利用中カート行をロック（ロック待ちの間に注文済になった場合は利用中カートなし＝明細0件として E-030-04）→全明細の在庫単位を識別子昇順でロック→手順4〜9を判定→在庫減算・注文・明細・配送先・状態履歴登録・カートを注文済→コミット。途中の失敗は全体をロールバックする。
4. カート操作（FR-020〜FR-025）：利用中カートの作成は「購入者ごとに状態＝利用中のカートは1件」の条件付き一意制約で守り、同時作成で一意違反となった側は作成済みの利用中カートを読み直して処理を続ける。明細の追加・変更・削除・クーポン操作は利用中カート行をロックしてから行う。
5. 支払（FR-031）：注文行をロック→所有・状態を判定（注文受付以外は決済要求を送らず E-031-05）→決済要求を1回送信し最大10秒待つ（ADDR-008。ロックを保持したまま）→承認は決済記録・注文の支払済・状態履歴を登録してコミット、否認・連携エラーは決済記録だけを登録してコミットしたうえで E-031-06・E-031-07 を返す。承認の反映途中の障害は全体をロールバックする（E-031-08）。「同じ注文の承認の決済記録は最大1件」を条件付き一意制約でも守る。
6. キャンセル（FR-034・FR-045）・出荷（FR-043）・配達完了（FR-044）：注文行をロック→状態を判定→更新（キャンセルは明細の在庫単位を識別子昇順でロックして在庫を戻す）→状態履歴→コミット。
7. 会員登録（FR-001）：正規化後メールアドレスの一意制約で守り、一意違反は E-001-02（メールアドレス登録済み）に変換する。
8. 初期データ一括投入（FR-060）：トランザクション開始直後に固定キーのトランザクション単位のアドバイザリロックを待機取得して一括投入どうしを直列化し、ロック取得後に一意性・参照整合性を判定する。削除（DELETE。TRUNCATE は使わない）・登録・成功の監査ログを1トランザクションで行う。登録時のメールアドレスの一意違反（同時の会員登録が先に確定）は E-060-05 に変換する。失敗時は全体をロールバックした後、別のトランザクションで失敗の監査ログを1件記録する。
9. 失敗の記録の分離：ログイン失敗の監査ログ（FR-002）、否認・連携エラーの決済記録（FR-031）、一括投入の失敗の監査ログ（FR-060）は、CMN-21 のただし書きどおりエラー終了時も残るように、業務データの変更とは別にコミットする。送信トークンの消費と結果の記録（11）も業務データの変更とは別にコミットする（r3 追加）。
10. 制約による最終防衛：在庫数量 0以上の検査制約、利用中カート・承認の決済記録の条件付き一意制約、メールアドレス・業務キーの一意制約をデータベースに定義する。違反は在庫不足・状態不正等の業務エラーまたはシステムエラーとして扱い、データを変更しない。

### 4.4 決定理由

OPT-001 は、ロック取得後に最新データで FR の手順をそのまま再実行するため、後着の要求が「逐次実行と同じ結果」になり、競合を CMN-19 の業務エラーで通知できる（DC-002）。在庫単位を識別子昇順でロックし、引当判定と減算を同じロックの中で行うことと、在庫数量0以上の制約で NFR-PF-07 を保証する（DC-001）。すべての制御がデータベースのロック・制約であるため実行単位を追加しても成立する（DC-004）。ロック順序を「親行→在庫単位→採番」に固定するため循環待ちが生じない（DC-006）。支払でロックを保持したまま決済の応答を待つことで、同時支払の後着は先着の確定後の状態で判定され、決済要求が二重に送信されない（IF-01-CON-01）。ただし否認・連携エラーの後に処理完了前の繰り返し操作が来ると新たな支払として送信されてしまうため、画面については1回限りの送信トークンで繰り返し操作そのものを1回分に限る（DC-005）。同じトークンの要求をトークン単位のアドバイザリロックで直列化するため、後着は先着の終了まで待ってから判定され、使用済みの要求も受付時点のデータで再判定して Web API の再送信と同じ判定順序で通知する（ログインは後述のとおり先着の結果を通知する。DC-007。r1 の結果画面への遷移は CMN-23・CMN-34 と通知が食い違うため改めた）。トークンの消費を業務処理より前の独立トランザクションで確定するため、先着がロールバックで終わっても消費は取り消されず、業務トランザクション外の反映（ログイン失敗の監査ログ、送信済みの決済要求）を伴う E-002-02・E-031-08 の後も後着は使用済みとなる（r3 改訂。OPT-005 は消費がロールバックで消え、OPT-006 は消費の確定が決済要求の送信後になる）。再判定が成立すると2回目の反映・送信・失敗の記録になる FR-002・FR-021・FR-031 だけその手順を省いて先着の結果を通知し、CMN-22・NFR-US-10・FR-002 6.2.9・FR-031 6.16.9 の「1回分だけ反映／決済要求は1回分だけ送信」を守る（DC-005）。ログインの使用済みトークンの要求では入力値による検索・照合を一切行わず先着の記録済みの結果だけを返すため、応答が入力値に依存せず、トークンを使い回しても監査ログなしに照合を試行できない。照合を行う要求（先着・トークンなし・未登録の任意の値）は必ず成否の監査ログを残すため、NFR-SC-22・FR-002 6.2.5 の「操作1回につき1件」と NFR-SC-14・VUL-11 の事後調査を損なわず、処理完了前の繰り返し操作は先着の1回分だけが反映・記録されるため CMN-22・FR-002 6.2.9 とも両立する（DC-005、DC-008。r4 改訂）。正規の繰り返し操作は同じ入力を送るため、先着の結果は再判定の結果と一致する。操作種別とトークンの組で消費を記録するため、別の操作で使用済みのトークンは当該操作では先着となり通常どおり処理される。OPT-008 は失敗の監査ログが重複し、OPT-009 は自分で発行・使用したトークンの使い回しを防げずログイン時のセッション識別子の再生成と両立しない。SERIALIZABLE・版番号は競合を再試行で解く方式で、自動再試行しない規定と CMN-19 の通知と合わない。
