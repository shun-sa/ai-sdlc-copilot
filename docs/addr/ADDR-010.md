## 3. 背景

### 3.1 判断が必要な理由

要件はDjangoテンプレートによるサーバーサイドレンダリングとJavaScriptの用途制限、メッセージ表示位置までを定めるが、共通レイアウトの分割単位と購入者向け・管理者向けでの再利用方法を定めていない。TASK-019 と TASK-020 は別Taskとして実装されるため、配置を先に決めないとヘッダー・メッセージ領域・入力エラー表示・ページングが二重に実装され、表示差異と修正漏れが生じる。

### 3.2 判断時の制約

- JavaScriptは確認ダイアログの表示と二重送信の防止に限って用い、HTMLの生成に用いない。
- SPAフレームワーク・フロントエンドのビルド工程・外部CDNを用いない。
- テンプレートの自動エスケープを無効化しない。
- 購入者向け機能を管理者へ表示しない（権限判定はサーバー側）。
- 業務ルールを画面側へ重複実装しない。
- 追加の依存ライブラリを導入しない。

### 4.3 決定内容

- テンプレートは `app/web/templates/` 配下に置き、次の構成とする。
  - `base.html`：全画面共通のレイアウト（文書構造、ヘッダー、ナビゲーション、メッセージ領域、フッター、スタイルシートの読込、ブロック定義）
  - `admin/base_admin.html`：`base.html` を継承する管理者向けレイアウト（管理用ナビゲーション、購入者向け導線を含めない）
  - `includes/`：共通部品（業務エラー・完了メッセージの表示、入力エラーの項目近傍表示、ページング、確認ダイアログ付き送信ボタン）
  - `buyer/`：購入者・来訪者向けの各画面テンプレート（SCR-001〜SCR-010）
  - `admin/`：管理者向けの各画面テンプレート（SCR-101〜SCR-103）
  - `error.html`：エラー画面（SCR-901）
- 共通部品は `includes/` のテンプレートを取り込んで使い、各画面で同等のHTMLを再実装しない。入力エラーは項目の近傍、業務エラー・完了メッセージは画面上部のメッセージ領域という配置を `base.html` と共通部品で固定する。
- CSSと最小限のJavaScriptは `app/web/static/` へ同梱し、外部CDNを参照しない。JavaScriptは確認ダイアログと二重送信防止に限定し、HTML生成に使わない。
- テンプレートは表示整形（書式・表示順の適用）だけを行い、業務判定を行わない。表示に必要な値（操作可否・金額内訳・ページ情報）はビューが services から受け取って渡す。
- 自動エスケープを無効化する記法（安全化フィルタ等）を使用しない。

### 4.4 決定理由

DC-001 と DC-002 は両立が必要であり、単一の基礎レイアウト＋ロール別レイアウト＋共通部品という3層構成が最小の重複で両方を満たす。独立レイアウト方式（OPT-002）は重複実装を招き、ライブラリ導入（OPT-003）は追加依存の制約に反する。表示整形のみをテンプレートの責務とすることで、業務ルールの画面側重複実装の禁止（Steering 4.2）を構造的に守れる。
