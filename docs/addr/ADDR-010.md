## 3. 背景

### 3.1 判断が必要な理由

FR-060 は運用者が定義ファイルと削除指定を指定して実行し、結果を運用者に示すこと、Web 画面・Web API から起動できないことを定めるが、サーバー上での実行方法・指定方法・結果の提示先・同時実行時の逐次化の方式は要件・Steering で指定されていない（OQ-FILE-002）。

### 3.2 判断時の制約

Steering 5章（具体的なデータ投入コマンドは後続工程で整備）、7章（--reset を本番環境で実行しない。適用範囲は OQ-PJ-002 で確認中）。運用者の権限はサーバーへのログイン権限（NFR-SC-12、NFR-SC-15）。処理時間60秒以内（NFR-PF-10、推奨）。

### 4.3 決定内容

OPT-001 を採用する。

1. 起動：管理コマンド load_initial_data として実装し、運用者がサーバーにログインして app コンテナ内で「python manage.py load_initial_data 定義ファイルのパス」（削除指定時は末尾に --reset）を1回実行する（Docker Compose では docker compose exec app で実行）。Web 画面・Web API の URL から呼び出す経路、サブプロセスとしてコマンドを起動する経路を作らない。
2. 実行時の指定：位置引数の定義ファイルのパス1件と、任意の --reset（既存データ（監査ログを除く）を削除してから投入する指定）だけを受け付ける。定義ファイルの指定なし、2件以上のパス、--reset 以外のコマンド固有の指定は E-060-01 とし、引数解析の誤りでも監査ログに失敗を1件記録してから終了する（Django 共通の実行環境の指定 --settings・--verbosity 等は実行条件として扱わない）。
3. 処理：ファイルの読込み（E-060-02）→記載形式の解釈（ADDR-009、E-060-03）→値域・一意性・参照整合性の全件判定（E-060-04・E-060-05）→削除・登録・成功の監査ログ（ADDR-004 DD-008 の1トランザクション、アドバイザリロックで直列化）の順に行う。定義ファイルのパスは引数で受け取ったものだけを開き、シェルを経由しない。
4. 結果の提示：成功時は標準出力に成功した旨とデータ別の投入件数（利用者・仕入先・商品分類・商品・商品分類所属・在庫単位・クーポン）を示し、終了コード0で終了する。失敗時は標準エラーに失敗の理由・何も投入しなかった旨・違反の全件（データ名・行番号・項目名・理由）を示し、終了コード1で終了する。項目の値・パスワード・メールアドレス・氏名は示さない。
5. ジョブ実行ログ：実行ごとに LOG-05（データ別の投入件数、違反時の違反内容（値なし））を、実行ごとに付与する識別子とともにアプリケーションログへ出力する（ADDR-013）。システム障害は LOG-02 にも出力する。
6. 削除指定の環境：FR-060 の振る舞いを変えず、実行環境による --reset の制限をプログラムに追加しない。稼働開始後の本番環境で --reset を用いないことは運用手順書で統制する（DCN-07、Steering 7章、NOQ-09 の暫定扱い）。

### 4.4 決定理由

OPT-001 は運用者のサーバーへのログイン権限を前提に、画面・API の経路を持たない（DC-001）。Django の設定・モデル・業務処理・パスワードの保持方式・ログ形式を画面・API と共有でき、追加依存がない（DC-004）。結果を標準出力・標準エラーと終了コードで示すため運用者が成功・失敗を判別でき（DC-002）、引数解析の誤りを E-060-01 として扱うことで指定誤りも監査ログに残せる（DC-003）。独立スクリプトは業務処理の二重実装になり、画面・API からの受付は要件に反する。
