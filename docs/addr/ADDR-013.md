## 3. 背景

### 3.1 判断が必要な理由

要件はログの種類・必須項目・出力禁止項目・保管期間・要求の識別子による追跡を定める（NFR-OM-01、NFR-OM-11、NFR-OM-18、NFR-SC-06）が、出力形式・出力先・要求の識別子の付与方法・機密項目の除外方法は定めていない。Django・AP サーバーの既定のログは要求先に検索条件を含み、例外の文言に項目値（例：一意制約違反の値）を含むことがあるため、方式の判断が必要。

### 3.2 判断時の制約

Steering 6.2（監視実装方式を本書で指定しない）。日時は日本時間（NFR-EN-04）。本番のログ保管基盤は未決（NOQ-01）。実行単位を追加しても追跡できること（NFR-PF-16）。

### 4.3 決定内容

OPT-001 を採用する。

1. 形式・出力先：アプリケーションログは1行1件の JSON（UTF-8）を標準出力へ出力する。全行に timestamp（日本時間 ISO 8601、ミリ秒まで）、level、log_type（LOG-01・LOG-02・LOG-03・LOG-05・LOG-06）、request_id を持たせ、種類ごとに次の項目を出力する。
   - LOG-01：user_id（ログイン時）、operation（処理名）、result（成功または ERR 種別と業務エラーの種類）、event（start・end）
   - LOG-02：user_id、error_type（system_error・integration_error）、exception_class、location（モジュール・関数・行）
   - LOG-03：method、path（検索条件を除いた要求先のパス）、status、user_id、duration_ms
   - LOG-05：job（initial_data_load）、result、counts（データ別件数）、violations（データ名・行番号・項目名・理由）
   - LOG-06：order_number、amount、currency、result、transaction_ref（承認時）、duration_ms、phase（request・response）
2. 要求の識別子：要求ごとにサーバーで UUID を生成し（要求ヘッダーの値は採用しない）、コンテキスト変数に保持して同じ要求の全行に付ける。応答ヘッダー X-Request-ID で返す。初期データ一括投入は実行ごとに生成する。
3. 機密項目の除外：出力する項目は上記の許可リストだけとし、要求本文・要求ヘッダー（Authorization・Cookie を含む）・クエリ文字列・メールアドレス・氏名・住所・電話番号・パスワード・ログイン状態を示す情報を出力しない。利用者は user_id（識別子）だけで示す。
4. 例外：例外は種類と発生箇所だけを出力し、例外の文言・引数・スタックトレースの値・データベースに渡した値を出力しない。Django 既定の django.request 等のロガーの出力は無効化し、上記の LOG-02 に置き換える。
5. AP サーバー：AP サーバー（ADDR-014）のアクセスログは無効にし、LOG-03 はアプリケーションのミドルウェアだけが出力する。
6. 保管：アプリケーションはログを保管しない。ENV-01 は Docker のログ機能で保持し、本番の90日保管・検索は本番基盤の収集・保管（NOQ-01・NOQ-02）で実現する（ASM-001）。

### 4.4 決定理由

OPT-001 は1行1件の JSON と固定の必須項目で全行を機械解析でき（DC-001）、サーバー生成の識別子をコンテキスト変数で全ログに付けるため LOG-01〜LOG-03・LOG-06 を1つの値で抽出できる（DC-002）。出力項目を許可リストで固定し、例外を種類と発生箇所に限り、AP サーバーのアクセスログを使わないことで、検索条件・項目値・機密情報が構造的に出力されない（DC-003）。標準出力への出力は本番基盤が未決でも収集方法を選ばない（DC-004）。外部ライブラリは追加依存の管理負担に見合わず、ローカルファイルは実行単位の追加と両立しない。
