## 3. 背景

### 3.1 判断が必要な理由

FR-031 6.16.4 手順5 は注文受付以外のとき「決済要求を送信しない」ことを求め、6.16.9 は「手順5 の状態判定から手順8・手順10・手順11 の結果反映までを1つの単位とし、その間に受け付けた同一注文への支払・キャンセルは、先の要求の結果反映後に判定する」と定める。一方で ADDR-001 DD-007 は応答時間の保護のためロック区間に決済呼び出しを含めないことを定め、ADDR-009 DD-005・INV-006 は承認の反映を送信後のロック取得と状態再確認で行うことを定めていた。この組合せでは、状態判定と決済要求の送信の間に同一注文のキャンセルが確定した場合に、要件が禁じる決済要求の送信が発生する（結合試験 IT-AI-GF-023／DEF-IT-001、AC-UC-007-019 (a)・VUL-07 違反）。要件は結果（送信しないこと・1単位であること）だけを定め、どの排他単位でこれを実現するかを定めていないため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- 注文状態は ST-PO-01〜ST-PO-06（注文受付・支払済・出荷済・配達完了・キャンセル済）に固定され、処理中を表す中間状態を追加できない（FR-031、D-10）。
- 競合専用の排他エラーコード・HTTPステータスを追加できない（api-contract 6.2、ADDR-001 INV-003）。
- IF-01 は要求（決済要求）と応答だけを定め、送信済み要求を打ち消す取消・返金のインターフェースを持たない（IF-01-SUP-02：返金は本システム外）。
- 技術スタックは Python 3.12・Django 5.2 LTS・PostgreSQL 16・Docker Compose（app・db の2サービス）に固定され、排他用の追加ミドルウェアを置けない（Steering 3章、NFR-EN-03）。
- 決済サービス（模擬）は app 内のプロセス内機能であり、外部ネットワークへ接続せず、1秒以内に応答する（FCN-01、NFR-EN-05、ADDR-009 DD-001・DD-002）。
- 更新系APIの応答時間は95パーセンタイル2.0秒以内（NFR-PF-02、NFR-PF-11）。

### 4.3 決定内容

- 支払（FR-031）は、注文の存在・所有の判定（手順4）に続いて、対象の注文行を `SELECT ... FOR UPDATE` でロックする。ロックの取得は手順5の状態判定より前に行う。ロック取得順序は 注文 → カート → 在庫単位（ID昇順）のまま変更しない（ADDR-001 DD-005）。
- 手順5の状態判定は、ロック取得後に読み直した注文状態に対して1回だけ行う。注文受付でない場合は決済ゲートウェイを呼び出さず、何も変更せずに INVALID_STATUS_TRANSITION（context の current_status はロック取得後に読み直した状態）を返す。
- 手順6の決済要求の送信、手順7の応答検証、手順8（承認）・手順10（否認）・手順11（連携エラー）の結果反映を、手順5と同じトランザクション・同じ注文行ロックの保持区間で行い、トランザクションのコミットでロックを解放する。承認時に状態を再判定しない（判定はロック取得後の1回だけとし、承認応答を受けた要求が決済記録として残らない経路を作らない）。
- ロック保持区間に置いてよい処理は、app プロセス内の決済ゲートウェイ境界の呼び出し（ADDR-009 DD-001・DD-002）、応答検証、決済記録・注文・注文状態履歴の更新、ADDR-005 のログ出力に限る。外部ネットワーク通信、スリープ、他プロセスへの待ちを置かない。模擬実装は待機を行わない（ADDR-009 決定内容）。
- 否認（手順10）・連携エラー（手順11）の決済記録も同じトランザクションで登録し、コミットが完了してから業務例外（PAYMENT_DECLINED／PAYMENT_SERVICE_ERROR）を送出する。業務例外の送出によってトランザクションをロールバックし、決済記録を失ってはならない。
- 同一注文への後着要求（支払・キャンセル）は、ロック待ちとして待機し、先の要求の結果反映が確定した後の状態で判定する（ADDR-001 DD-008・INV-006）。支払が先に確定した場合、後着のキャンセルは支払済からのキャンセルとして成功し、決済記録を変更しない（FR-031 6.16.9、BR-UC-007-010）。
- キャンセル（FR-034、FR-045）は、従来どおり注文行をロックしてから状態を判定する（ADDR-001 DD-002）。これにより支払とキャンセルは同一の注文行ロックで直列化される。
- 決済ゲートウェイ境界の締切10秒（ADDR-009 DD-003）は、同時に注文行ロックの保持時間の上限として機能する。ネットワーク呼び出しを伴う実決済サービスへ差し替える場合は、本ADDRを更新してロック区間と応答時間の再判断を行ってから実施する。
- 本ADDRは、ADDR-009 DD-005・INV-006（承認の反映を送信後のロック取得と状態再確認で行う）および ADDR-001 DD-007・INV-004（ロック区間に決済サービスの呼び出しを含めない）を更新する。更新の理由は、従来の決定が FR-031 6.16.4 手順5・6.16.9 と AC-UC-007-019 (a)・VUL-07 を満たさないことが結合試験で決定的に再現したためである。両ADDRの該当記述は本ADDRを正本とし、両ADDRのその他の決定（決済ゲートウェイの配置・要求応答項目・締切・ログ、行ロックによる直列化・ロック順序）は変更しない。

### 4.4 決定理由

DC-001 と DC-002 は、状態判定と決済要求の送信の間に他要求の確定を挟ませないことを要求する。注文状態を増やせず（DC-006）、送信済み要求の取消手段も無い（IF-01-SUP-02）ため、判定・送信・反映を同一の排他区間に入れる OPT-001 以外に要件を満たす方式が無い。ADDR-001 DD-007 の本来の意図は「ロック保持中に外部の待ちを発生させない」ことであり、本リリースの決済サービスは app プロセス内の模擬機能で外部I/O・待機を行わず1秒以内に応答する（FCN-01、NFR-EN-05、ADDR-009）。したがってロック保持時間の増加は無視できる水準であり、DC-004・DC-005 は「外部ネットワーク通信・スリープ・他プロセス待ちをロック区間に置かない」という形に限定して維持できる。アドバイザリロック（OPT-003）は行ロックと別系統の排他を増やすだけで、ロックを保持したまま呼び出す点は同じであり利点が無い。中間状態（OPT-004）と補償（OPT-005）はいずれも要件に無い状態・外部操作の追加となるため採用しない。なお本決定により、同一注文への同時支払（AC-UC-007-013）では後着要求がロック待ちの後に支払済を読み、決済要求を送信せずに INVALID_STATUS_TRANSITION となるため、承認済み決済記録は1件に保たれる（IF-01-CON-01）。
