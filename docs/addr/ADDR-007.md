## 3. 背景

### 3.1 判断が必要な理由

エラー応答の形式・エラーコード・context は受領仕様で確定しているが、それを全API・全画面へ一貫して適用する仕組み（どこで例外を生成し、どこで応答へ変換し、判定順序をどう保証するか）が未提供である。各ビューで個別に応答を組み立てると、判定順序（CMN-14）・details の全項目列挙・内部情報の非表示を全機能で保証できない。

### 3.2 判断時の制約

- 判定順序は①認証（401）→②権限（403）→③入力形式（400）→④対象の存在・所有（404）→⑤状態（409）→⑥業務ルール（409）で、先に該当したエラーのみを返す（CMN-14、Steering 7.1）。
- VALIDATION_ERROR は不備のある全項目を details に列挙する（Steering 6章）。
- 他の購入者の注文を指定した場合は NOT_FOUND（404）とし存在有無を明かさない（api-contract 6.1、PRM-01）。
- 応答にスタックトレース・SQL・ファイルパス・ライブラリ名を含めない（NFR-SC-10）。
- 競合専用のエラーコードを追加しない（api-contract 6.2、ADDR-001）。

### 4.3 決定内容

- shop/common にエラーコード定義（api-contract 6.2 の一覧と HTTP ステータスの対応表）と業務例外の基底クラスを置く。基底クラスは code・http_status・message（日本語）・details（項目名と理由の配列）・context（機械判読用の辞書）を持つ。
- 個別の業務エラーは基底クラスの派生として定義する（例：在庫不足・数量上限超過・クーポン各種・状態不正・対象なし・権限なし・認証要求）。context の内容は api-contract 6.3 の表に従う。
- services 層は、業務判定に失敗した場合に対応する業務例外を送出する。応答の組み立て（JSON 化・HTTP ステータス付与）を services では行わない。
- api 層は DRF の設定で単一の例外ハンドラを登録し、業務例外・DRF の検証例外・権限例外・認証例外・未捕捉例外を受けて、常に共通形式へ変換する。未捕捉例外は INTERNAL_ERROR（500）とし、内部情報を応答に含めない。
- 判定順序は次の実行順で固定する。①DRF 認証クラス（ADDR-002）→②DRF 権限クラス（ロール判定）→③シリアライザによる入力検証（全項目を検証し details へ列挙）→④対象の取得と所有判定（他購入者の対象は NOT_FOUND）→⑤services での状態判定→⑥services での業務ルール判定。
- 入力検証はシリアライザで一括実行し、最初の項目で中断せず不備のある全項目を details に列挙する。各FRが定める判定順序（手順）はその機能の services 内で保つ。
- 対象の取得と所有判定は共通ヘルパー（例：所有者一致でなければ対象なしとする取得関数）に集約し、各ビューで個別実装しない。
- ページング（page の検証、results・page・page_size・total_count・total_pages の組み立て）も shop/common に共通実装を置き、各一覧APIから使う（NFR-PF-08、ADDR-006 DD-005）。
- 画面（web 層）は同じ業務例外を捕捉し、入力エラーは該当項目の近傍へ、業務エラーは画面上部のメッセージ領域へ、同じ message を表示する。システムエラーは SCR-901 を表示する。
- 本番環境ではデバッグ表示を無効化し、エラー応答・画面に内部情報を出さない（NFR-SC-10）。例外の詳細はログにのみ出力する（ADDR-005 DD-007）。

### 4.4 決定理由

判定順序と応答形式は25機能すべてに共通する横断要件であり、生成箇所を1か所に集約しなければ一貫性を検証できない（DC-001・DC-002）。DRF は認証・権限・検証の実行順が明確に定義されており、残る④〜⑥を services の呼び出し順に対応させることで、CMN-14 の順序をフレームワークの構造として保証できる。例外を services で送出し応答変換を api で行う分離は、画面（web）でも同じ判定結果を再利用できるため、Steering 4.2 の重複実装禁止とも整合する（DC-004）。
