## 3. 背景

### 3.1 判断が必要な理由

要件はログの形式（JSON Lines）・必須項目・禁止項目・保管90日を定めるが、出力先（標準出力かファイルか）とローテーション手段を定めていない。出力先が未確定だと、TASK-003 のログ設定とDocker Compose の構成、障害調査手順（NFR-OM-18）が一意に決まらない。

### 3.2 判断時の制約

- 外部のログ収集サービス・インターネットへ接続しない（NFR-EN-05）。
- Docker Compose のサービスは app と db の2つで、収集基盤コンテナを追加しない。
- 本番環境の基盤は未選定（OQ-PJ-001）であり、本リリースの実装は検証環境で成立する必要がある。
- パスワード・認証トークン・メールアドレス・氏名・住所・電話番号を出力しない。
- app はプロセス数・コンテナ数の増設で拡張できること（NFR-PF-16）。

### 4.3 決定内容

- アプリケーションログ（リクエストログ・エラーログ・運用コマンドの実行ログ）は、Pythonのロギングで標準出力へ1行1JSONとして出力する。ファイルハンドラ・アプリ内ローテーションは実装しない。
- 出力整形は `common` の単一のフォーマッタで行い、必須項目（timestamp・level・request_id・method・path・status・user_id・duration_ms）を1か所で組み立てる。禁止項目は出力対象へ渡さない（マスキングではなく非出力）。`path` はクエリ文字列を除いたパス部分だけを組み立て（検索条件にメールアドレスが含まれ得るため、NFR-SC-06 後段）、要求URL全体・クエリ文字列・要求本文をログレコードへ渡さない。
- `request_id` は共通ミドルウェアで採番・引継ぎし、同一リクエストの全行と応答ヘッダーへ同じ値を使う。
- 標準エラー出力は例外のトレースを含み得るため、アプリケーションログの正規の出力先としては用いず、未捕捉例外も標準出力のJSON行として記録する（利用者への応答には内部情報を含めない）。
- 保管・ローテーションは基盤側で設定する。検証環境は Docker Compose のログ設定（ドライバとサイズ・世代の上限）で行い、本番環境の保管90日は基盤選定時（OQ-PJ-001）に設定する。
- 監査ログはDB（D-15）へ記録し、アプリケーションログと混在させない。

### 4.4 決定理由

app の増設でスケールする前提（DC-003）では、複数プロセスが同一ファイルへ書く方式は行の混在・欠落の危険があり採用できない。標準出力へ書く方式はコンテナの標準的な運用と一致し、保管・ローテーションを基盤設定へ委ねられるため、外部接続なし（DC-005）という制約とも両立する。90日保管は本番基盤の設定事項であり、アプリ側の実装では担保できないため、設定で満たす方式を選ぶほうが責任分界が明確になる。
