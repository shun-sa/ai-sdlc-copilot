## 3. 背景

### 3.1 判断が必要な理由

要件は応答時間の目標値（照会系1.0秒以内、3年後データ量でも同じ）とデータの一意条件を定めるが、それを実現する一意制約・索引・クエリ構成を定めていない。TASK-002 の Notes は一意制約・索引の実現方式を、TASK-005・TASK-016 はクエリ構成を独立ADDR工程へ委ねている。確定しないと、3年後データ量（注文110,000件・注文明細330,000件・会員10,000件）での性能が実装者ごとに変わり、N+1クエリによる目標未達を招く。

### 3.2 判断時の制約

- 保持しない算出項目（税込価格・最低価格・在庫有無）をモデルへ持たせない。
- 一覧の応答件数上限（20件／50件）とページング形式を変更しない。
- 追加のDB拡張モジュール・外部検索基盤を導入しない（app と db のみの構成）。
- 監査ログ・注文状態履歴は追記のみとする。
- 同時実行制御は ADDR-003 の行ロック方式に従う（本ADDRで排他方式を再定義しない）。

### 4.3 決定内容

- 一意制約（マイグレーションで定義）：利用者の正規化済みメールアドレス、仕入先コード、分類コード、商品コード、SKU、クーポンコード、注文番号、認証トークンのハッシュ値。商品分類所属は（商品、商品分類）の複合一意。制約には安定した名称を明示的に付与し、既定の自動生成名に依存しない（ADDR-011 の「制約名→業務例外」の対応表が制約名を鍵に写像するため）。利用者のメールアドレス一意制約の違反は `EMAIL_ALREADY_REGISTERED`（409）へ写像される（写像表の正本は ADDR-011、本ADDRでは写像を定義しない）。
- 部分（条件付き）一意制約：商品分類名は同じ親分類の中で一意とし、親分類を持たない最上位の分類どうしの一意性は「親分類が値なし」を条件とする条件付き一意制約で表現する。購入者の未注文カートも条件付き一意制約で1件に限定する。
- 検査制約：在庫数量は0以上（ADDR-003 の業務判定が先行し、制約は最後の防御として働く）。
- 索引：外部キー列はDjangoの既定どおり索引を作る。加えて、商品一覧（公開状態・表示順）、在庫単位（商品、SKU）、在庫数量（低在庫絞り込み）、注文（購入者＋注文日時の降順）、注文（状態＋注文日時の降順）、注文明細（注文）、注文状態履歴（注文）、監査ログ（発生日時）に索引を定義する。
- クエリ構成：一覧・詳細の取得では関連データを結合取得（`select_related`）または一括取得（`prefetch_related`）し、ループ内での追加問い合わせを行わない。最低価格・在庫有無などの算出項目は集約関数または取得済みの在庫単位から算出し、列として保持しない。件数は同一条件の件数取得で求め、全件取得して数えない。ページングは件数上限に従った範囲取得で行う。
- 商品名の部分一致検索は索引を用いない全件走査となるが、対象規模（3年後で商品600件）では目標応答時間に収まるため、拡張の導入は行わない。
- 性能確認は3年後相当データ量を投入して照会系・更新系・画面表示の応答時間を測定する。

### 4.4 決定理由

DC-002 を実装完了時点で裏付けるには、検索経路を設計で確定し索引として記録する必要がある（OPT-002 では裏付けがない）。一方、対象データ量は3年後でも注文110,000件規模であり、標準的なB木索引と結合取得で目標を満たせる見込みが立つため、拡張導入（OPT-003）は費用対効果が合わない。条件付き一意制約を用いるのは、親分類が値なしの行どうしでは通常の複合一意制約が機能せず、「最上位の分類どうしでも分類名が一意」という要件を満たせないためである。
