## 3. 背景

### 3.1 判断が必要な理由

要件は保存形式の性質（ソルト付き一方向ハッシュ、利用者ごとに異なるソルト、平文・可逆暗号の禁止）だけを定め、アルゴリズムとパラメータを定めていない。選択により認証系の応答時間（NFR-PF-09）と依存ライブラリの有無（NFR-SC-11、NFR-EN-12）が変わるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- 技術スタックは Python 3.12・Django 5.2 LTS に固定されている（Steering 3章）。追加の依存ライブラリは脆弱性確認・ライセンス確認・サポート期限管理の対象を増やす（NFR-SC-11、NFR-EN-12、NFR-EN-10）。
- 認証系APIの応答時間は95パーセンタイルで2.0秒以内（NFR-PF-09。ハッシュ計算を含む区間）。
- 初期データ一括投入は定義ファイルの平文パスワードを投入時にハッシュ化し、平文を保持しない（NFR-SC-01、FILE-RULE-004）。
- 初期データ一括投入は1,157件を60秒以内で完了することが推奨目標（NFR-PF-10）。

|---|---|---|---|---|---|

### 4.3 決定内容

- Django の PASSWORD_HASHERS の先頭を PBKDF2PasswordHasher（PBKDF2-HMAC-SHA256）とし、反復回数は採用する Django 5.2 の既定値をそのまま用いる。既定値より低い値へ変更しない。
- ソルトは Django のハッシュ機構が利用者ごとに生成するランダム値を用い、ハッシュ文字列（アルゴリズム識別子・反復回数・ソルト・ダイジェスト）を利用者データのパスワードハッシュ項目へ保存する。
- パスワードの保存は Django の make_password 相当の標準関数、検証は check_password 相当の標準関数のみで行う。独自のハッシュ計算・比較を実装しない。
- 会員登録（FR-001）と初期データ一括投入（FR-060、TASK-014）は同一の保存関数を呼び、定義ファイルの平文パスワードをメモリ上でのみ扱い、平文を保存・記録・出力しない。
- パスワード検証の比較は標準関数の定数時間比較に委ね、文字列の等価比較を自前で行わない。
- 既定ハッシャを将来変更する場合は、検証時の自動再ハッシュ機構（標準機能）に委ね、保存済みハッシュの一括変換を行わない。
- パスワード・パスワードハッシュをログ・標準出力・API応答・画面に出力しない（NFR-SC-06、ADDR-005）。
- パスワードの文字数・文字種の条件（NFR-SC-16）は入力検証（ADDR-007 の入力検証層）で判定し、ハッシュ化の前に行う。

### 4.4 決定理由

NFR-SC-01 は方式そのものを指定しておらず、要求されるのは「利用者ごとに異なるソルトを持つ一方向ハッシュ」である。Django 標準の PBKDF2-HMAC-SHA256（OPT-001）はこれを満たし、固定スタック内で追加依存を生まない（DC-003）。Argon2id・bcrypt（OPT-002・OPT-003）は安全性の面で選択肢となり得るが、依存追加により NFR-SC-11・NFR-EN-12・NFR-EN-10 の管理対象が増える一方、要件が求める保存形式の充足度は同じである。自前実装（OPT-004）は反復回数による計算コストを持たず採用しない。応答時間（DC-002）は、1回のログイン・会員登録につきハッシュ計算1回であり、性能テストで確認する（ASM-001）。
