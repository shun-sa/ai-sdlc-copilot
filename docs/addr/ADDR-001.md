## 3. 背景

### 3.1 判断が必要な理由

要件は同時実行の「結果」（CMN-19・CMN-20・CMN-23、NFR-PF-07）だけを定め、その結果を成立させる実現方式を定めていない。方式には行ロック・楽観ロック・分離レベルの引き上げなど複数の合理的な選択肢があり、選択によって競合時に返す業務エラーの成立可否と更新系の応答時間（NFR-PF-02）が変わるため、実装前に一意に決める必要がある。

### 3.2 判断時の制約

- CMN-20 は「参照した時点から更新する時点までの間に他の要求がデータを更新したかどうかの検出は行わず、更新する時点のデータに対して各機能の判定を行う」と定めるため、更新競合を検出して利用者へ返す方式は採用できない。
- 競合専用の排他エラーコードを追加できない（api-contract 6.2）。
- 技術スタックは Python 3.12・Django 5.2 LTS・PostgreSQL 16・Docker Compose（app・db の2サービス）に固定され、排他制御のための追加ミドルウェアを置けない（Steering 3章、NFR-EN-03）。
- 利用者の状態を app のプロセス内に保持できない（NFR-PF-16）ため、app プロセス内の排他は成立しない。

### 4.3 決定内容

- トランザクション分離レベルは PostgreSQL 既定の READ COMMITTED を変更しない。更新を伴う機能（FR-021〜FR-025, FR-030, FR-031, FR-034, FR-043, FR-044, FR-045, FR-060）は、その機能のデータ変更全体を1つのDBトランザクション（Django の atomic ブロック）に入れる。
- 在庫引当（FR-030 手順9・手順10）では、判定の直前に対象の全在庫単位行を在庫単位ID（stock_unit_id）の昇順で FOR UPDATE により行ロックし、ロック取得後の在庫数量で不足判定と減算を行う。不足が1件でもあれば在庫数量を変更せず INSUFFICIENT_STOCK を返す。
- 注文状態の変更（FR-031, FR-034, FR-043, FR-044, FR-045）では、対象の注文行を FOR UPDATE でロックしてから現在の状態を読み、遷移可否を判定する。遷移できない場合は INVALID_STATUS_TRANSITION（context に current_status）を返す。
- 同一カートの二重送信（FR-030、CMN-23）では、利用中カート行を FOR UPDATE でロックしてから明細件数を判定し、同一トランザクション内でカートを注文済へ変更する。後着の要求はロック解放後に明細0件（利用中カートなし）として CART_EMPTY を返す。
- カート明細の追加・数量変更・削除（FR-021〜FR-023）では、カート行をロックしてから明細を操作し、同一カートへの同時操作を直列化する。削除済み明細への後着操作は対象なし（NOT_FOUND）とする。
- 注文キャンセルの在庫戻し（FR-034, FR-045）では、注文行をロックした後に対象の在庫単位行を在庫単位IDの昇順でロックして在庫数量を加算する。
- 会員登録の競合（FR-001）は、メールアドレス（正規化後）の一意制約違反を捕捉して EMAIL_ALREADY_REGISTERED に変換する。
- ロック取得順序を「注文（D-10）→ カート（D-08）→ 在庫単位（D-06、ID昇順）」に統一する。
- ロック待ちは待機とし、NOWAIT・SKIP LOCKED を使わない。待機中に競合相手が確定した場合は、確定後の値で改めて業務判定を行う。
- 決済サービス（模擬）の呼び出しは、注文行をロックした同一トランザクションの内側で行い、状態判定から結果反映までを1つの単位とする（FR-031 6.16.9、ADDR-013）。ロック保持中に置けるのは app プロセス内の呼び出しに限り、外部ネットワーク通信・スリープ・他プロセスへの待ちを含めない。

### 4.4 決定理由

DC-003 により、競合の検出を利用者へ通知する楽観ロック（OPT-002）は採用できない。行ロック（OPT-001）は、判定と更新の間に他要求が割り込まないため「更新する時点のデータに対して判定する」という CMN-20 の規定をそのまま実装でき、競合の結果を既存の業務エラーだけで表現できる（DC-002）。対象行は1要求あたり最大10明細程度（FR-030 の数量上限と注文明細の件数）であり、ロック区間を判定・更新だけに限定すれば NFR-PF-02 の2.0秒を満たせる。SERIALIZABLE（OPT-003）は再試行が前提となり応答時間がばらつくため、本リリースの規模では利点が制約を上回らない。
