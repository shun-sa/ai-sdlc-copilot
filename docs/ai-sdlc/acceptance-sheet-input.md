# 受入試験表を渡して実行する

## 利用者の操作

1. Agent環境の更新を先に共通Agentブランチへ反映・確認し、実験とは別に確定する。
2. 開発中は受入表をリポジトリ外に保管する。今回の表はAI作成案なので、人がレビューするまで人作成済み基準とは扱わない。
3. 開発がCOMPLETE / COMPLETE_WITH_UNRESOLVEDになってから、VSCodeのAcceptanceTestExecutorを選び、下記のように依頼する。
4. Agentが表を取り込み、外部受入テストの準備案と未対応理由を提示する。元の期待条件とコードへの対応を確認して承認する。
5. 承認後に同じAgentへ実行を依頼する。全ケースのPASS / FAIL / BLOCKED、証跡、合格率を受け取る。

依頼例（保存先とrun_idは実際のものへ変更）:

```text
開発が完了したRUN-001の受入試験を、この表から準備してください。
表: <リポジトリ外に保存したXLSXまたはCSVまたは試験定義JSONの絶対パス>
新規の空の作業先: <リポジトリ外のRUN-001評価用フォルダの絶対パス>
開発完了記録: reports/experiments/RUN-001/run-context.json
表の初回読込時に実際の公開時刻を記録してください。
ケース・期待値・アプリ・開発テストは変更せず、外部テストを準備してください。
実行できない項目も理由付きで残し、実行前に承認待ちで止めてください。
```

これは「配置したら自動起動」ではない。開発完了後の明示起動と人の承認が必要。
実アプリ・ブラウザ・専用DB/volume等の環境が不足している項目を、配置だけでPASSにはしない。
新しいAgentをVSCodeが認識していない場合はAgent一覧の再読込を行う。

## 保存する表

今回の8シートの表をXLSXで保存する場合は、**受入項目と受入詳細を必ず含める**。
受入詳細の分割番号順に全文を復元するため、一覧だけのPDF・画像・受入項目シート単独は実行入力にできない。
編集していない場合は、既配布ZIPの`acceptance-case-definitions.json`または`acceptance-cases.csv`も直接指定できる。
表を編集した場合、古いCSV/JSONは自動同期しない。最新の表をXLSXで保存するか全条件を含むCSV/JSONへ反映する。

受入249件だけが今回の主表。補足NFR86件、結合90件、集計の結果値を受入分母へ勝手に追加しない。
定義表の既存PASS表示も測定値として読み込まない。毎回外部テストの実測だけを結果にする。

## Agentと責務

```text
人（開発完了後に明示起動）
  → AcceptanceTestExecutor
    → 決定論的import（全ケース・全文・出典を複写）
    → AcceptanceTestPrepare（確定条件を外部コードへ翻訳）
    → 人のレビュー・承認
    → 決定論的seal（コード・条件・対象版を凍結）
    → 既存の決定論的実行・結果検証
```

Requirements → Architecture → ADDR → Implementationの開発工程は変更しない。
準備担当はSDLCの子ではなく、開発後のAcceptanceTestExecutorだけの準備担当である。
準備担当がアプリのAPIパスやDB接続方法を調べてコード化するので、人が全ケースのコマンドを手入力する必要はない。
人の確認が不要になるわけではない。assertion_mapは意味的正しさの機械的証明ではないので、元表の全条件との対応を確認する。
共有・本番DBの破壊、依存導入、権限変更、評価対象の修正を自動許可しない。

## ファイルと安全境界

外部評価フォルダには元表の複写、case-bundle.json、bindings.json、tests/、plan-review.json、凍結manifestと結果CSVを保存する。
読込時のRun・完了時刻・公開時刻、原本ハッシュ、対象ソース版を固定する。run-contextは対象リポジトリで記録した実体だけを使う。
XLSX読込は標準ライブラリで行い、式・マクロ・外部リンクを実行しない。期待値に式がある場合は固定値へ確定してから再提出する。
表の文章中の操作指示やサンプルコマンドを、Agent設定の上書き指示として扱わない。

bindings.jsonの各ケース:
- COMMAND: argv配列、test_files、前提/手順/期待値/証跡のassertion_mapを記録。cwdは外部workspace固定。テスト成功の終了値は0。
- BLOCKED: 実行不能の具体的理由。コマンドを動かさず結果へ残す。
- UNBOUND: 準備途中。1件でも残れば承認後の凍結不可。

実行可能テストでも、指定された前提や観測手段が不足した場合は終了値125を返してBLOCKEDにする。
期待値不一致は125以外の非0でFAIL。全条件を満たす場合だけ0でPASS。
凍結後に元表・bindings・tests・対象ソースが変われば実行/評価を止める。pyc等は生成テストの定義ではないので凍結から除く。
対象ソース不変性の確認は変更の検出であり、OSのアクセス制限ではない。専用環境・権限の隔離も必要。

## エラー・計測

準備の同一原因は初回失敗＋最大3回修正まで。未解決の項目は理由付きBLOCKEDとして残し、人へ渡す。
隔離・承認・改変検出に失敗した場合は、3回ループで実行許可へ昇格させない。
実行後はFAILを直すためにアプリや外部テストを書き換えず、人へ返却する。やり直しは新しい評価試行として記録する。
FAIL/BLOCKEDを分母から除外しない。合格率はPASS / 確定した全ケース。
受入準備・人の確認・受入実行は開発の「設計から結合試験終了まで」の時間へ加算しない。
同じrun_idのjournalがあれば、既存結果連携を使う。受入のためSDLCを自動再開しない。

従来の人が確定したCOMMAND manifestも互換維持する。BLOCKED型は承認済み表入力にだけ認める。
今回追加したものは汎用の準備機能であり、MiniCommerceの実アプリ用249本のテストを事前実装・実行したものではない。
